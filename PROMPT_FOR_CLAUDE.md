# Инструкция Claude Code — workflow с SESSION_LOG.md

Этот файл описывает, как Claude Code работает в репозитории
whois-watcher в связке с планирующим Claude'ом в Claude.ai чате.

## Общая схема

```
1. Пользователь → планирующий Claude (chat): обсуждение задачи
2. Планирующий Claude → пользователь: промпт со спецификацией
3. Пользователь → Claude Code (сервер): копия промпта
4. Claude Code: выполняет, коммитит, пушит, пишет в SESSION_LOG.md
5. GitHub Action: триггерится на push в SESSION_LOG.md
6. Telegram-канал: получает уведомление со свежей записью
7. Пользователь видит уведомление, шлёт "." в чат
8. Планирующий Claude: фетчит SESSION_LOG.md, готовит следующий промпт
```

## Обязательные действия Claude Code после задачи

После полного выполнения задачи из промпта:

1. **Запустить тесты** — `pytest` (или релевантную часть)
2. **Запустить линтер** — `ruff check src tests`, `mypy src`
3. **Сделать коммиты** по плану из промпта (атомарные)
4. **Добавить запись в SESSION_LOG.md** (НОВЫЕ записи СВЕРХУ файла,
   ПОД заголовком журнала, но НАД предыдущими записями)
5. **Сделать финальный push** — это запушит и коммиты задачи,
   и SESSION_LOG.md в одной операции
6. **Сообщить пользователю** что сессия завершена

После пуша GitHub Action автоматически отправит уведомление в
Telegram-канал.

## Шаблон записи в SESSION_LOG.md

Использовать `scripts/send-session-log.sh "Короткое описание"` чтобы
добавить skeleton-запись, потом заполнить детали.

Формат записи:

```markdown
## Session YYYY-MM-DD HH:MM — Подэтап N: Короткое название

**Задача:** Одно-два предложения о цели задачи.

**Выполнено:**
- Конкретный пункт 1
- Конкретный пункт 2
- ...

**Изменённые/новые файлы:**
- `path/to/file1.ext`
- `path/to/file2.ext`

**Коммиты:**
- `<sha>` — `subject`

**Проверки:**
- pytest: N tests passing (было M)
- mypy strict: clean (X files)
- ruff: clean
- Real-world Telegram tests: если применимо

**Архитектурные решения / Открытые вопросы:**
- ...

**Затраченное время:** ~XX минут

---
```

## Что НЕ писать в SESSION_LOG.md

Журнал публичный (репо open-source). НЕ указывай:

- **Реальные домены пользователей бота.** Используй "тестовый домен",
  "произвольный домен", или конкретный публичный пример типа
  `example.com`, `yandex.ru` если это явно для демонстрации фичи
- **Telegram ID, username реальных пользователей**
- **Runtime-метрики прода** — количество пользователей в БД,
  количество доменов, IP сервера, hostname
- **Значения из `.env`** — URL прокси, токены, секреты
- **Внутренние пометки** типа «не пушить пока без правки X» — это
  для коммит-сообщений или PR-описаний, не для журнала

## Что МОЖНО (и нужно) писать

- Имена создаваемых/изменяемых файлов в репо
- Названия коммитов и тегов
- Названия архитектурных решений (со ссылкой на ADR где есть)
- Названия новых тестов
- **Общее** количество тестов («493 passing») — это aggregate
- Время потраченное на сессию
- Открытые архитектурные вопросы для следующей сессии

## Защита от прямого редактирования SESSION_LOG.md

НЕ редактируй старые записи. Если что-то нужно исправить — добавь
новую запись с пометкой "Поправка к Session YYYY-MM-DD HH:MM".

История важна для прозрачности процесса.

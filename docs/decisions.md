# Лог принятых решений (ADR)

Каждое решение зафиксировано с обоснованием. Не меняйте без обсуждения — если что-то кажется не так, открывайте issue или обсуждайте.

---

## 001. Python 3.11+ как основной язык

**Решение:** Python 3.11+.

**Почему:**
- Богатая экосистема для Telegram-ботов, WHOIS, async
- Быстрая разработка
- aiogram 3.x — зрелый асинхронный фреймворк
- Альтернативы (Go, Node.js) дают выигрыш в производительности, но проигрывают в скорости разработки

---

## 002. PostgreSQL как основная БД

**Решение:** PostgreSQL 16.

**Почему:**
- При ожидаемых объёмах (десятки тысяч пользователей × до 50K доменов на пользователя) SQLite не подходит — блокировки при параллельных записях
- JSONB для хранения сырых WHOIS-ответов
- Партиционирование больших таблиц (`sent_notifications`, `system_events`) по дате при росте
- Условные индексы (например, `next_check_at WHERE next_check_at IS NOT NULL`)
- Полнотекстовый поиск, если понадобится

**Отвергнуто:** MongoDB (избыточно), MySQL (Postgres лучше для наших нужд).

## 003. Webhook, не long polling

**Решение:** webhook через Nginx + HTTPS.

**Почему:**
- На десятках тысяч пользователей long polling даёт лишнюю задержку и нагрузку
- Webhook масштабируется лучше
- Telegram сам решает, когда нам слать обновления

**Цена:** требуется домен и SSL-сертификат. Решается Let's Encrypt бесплатно.

**Почему:**

**Отвергнуто:** python-telegram-bot (тяжелее, async добавлен позже).

## 005. ARQ как очередь задач

**Решение:** ARQ.

**Почему:**
- Нативно async (важно — у нас всё на asyncio)
- Использует Redis (который у нас и так есть)
- Легче Celery, нет необходимости в Celery beat
- Поддержка cron-задач из коробки

**Отвергнуто:** Celery (избыточно сложен для нашего размера, sync-ориентирован), Dramatiq (хорош, но Celery-подобный).

## 006. Общий кэш WHOIS на всех пользователей

**Решение:** одна таблица `whois_cache` с PK = `domain`. Все пользователи с одним доменом обслуживаются одной записью.

**Почему:**
- Дата истечения домена не зависит от пользователя
- Тысячи пользователей на одном популярном домене — одна WHOIS-проверка для всех
- Сильно снижает нагрузку на WHOIS-серверы

**Следствие:** удаление домена из `user_domains` не удаляет из `whois_cache`. Сборщик мусора чистит сиротские записи.

## 007. Адаптивный TTL проверок

**Решение:** частота WHOIS-проверки зависит от близости даты истечения:
- > 90 дней → раз в 30 дней
- 30–90 → раз в 7 дней
- 7–30 → раз в 2 дня
- < 7 → раз в день
- После истечения → раз в день ещё 45 дней

**Почему:**
- Дата истечения почти никогда не меняется
- Чем ближе край, тем выше цена ошибки
- Снижает нагрузку в 10-20 раз по сравнению с "проверяем всё ежедневно"

**Значения в `src/config/limits.py`**, можно крутить.

## 008. RDAP как основной протокол, WHOIS как fallback

**Решение:** сначала RDAP (через `whoisit`), при неудаче — WHOIS на 43 порту.

**Почему:**
- RDAP — современный стандарт, JSON-ответы, нормальные rate limits
- WHOIS — текстовый, парсинг хрупкий, лимиты жёстче
- Большинство gTLD (.com, .net, .org, .io) поддерживают RDAP
- Многие ccTLD (включая .ru) пока только WHOIS

**Не используем:** платные WHOIS-API (WhoisXML, etc.). Бесплатный проект, бюджет ограничен.

## 009. Три независимых процесса

**Решение:** бот (webhook), воркеры, планировщик — отдельные процессы.

**Почему:**
- Бот должен отвечать Telegram быстро, не блокироваться на WHOIS
- Воркеры можно масштабировать горизонтально независимо
- Падение воркера не валит бота, и наоборот
- Чёткое разделение ответственности

## 010. Бесплатный проект без тарифов

**Решение:** никаких платных функций, лимиты — только защита от абьюза.

**Почему:** так решил автор. Проект сообщества.

- Бюджет проекта — фиксированно низкий

## 012. Webhook для уведомлений о смене статусов закладываем сразу

**Решение:** при каждой WHOIS-проверке сравниваем новые значения со старыми. Если изменилось — уведомляем подписчиков.

**Отслеживаемые типы смены:**
- `expires_at` — продление или укорочение
- `registrar` — трансфер
- `name_servers` — смена хостинга
- `status[]` — блокировки и спецстатусы

**Гранулярность:** на уровне `user_domains` отдельные флаги для каждого типа.

**Дефолты:** `expiry=on, registrar=on, status=on, ns=off` (NS меняется слишком часто и обычно осознанно).

## 017. `/delete_me` через две команды

**Решение:** `/delete_me` показывает предупреждение, требует подтверждения через `/delete_me_confirm`.

**Почему:**
- Защита от случайного удаления

**Реализация:** Redis-флаг `delete_pending:{user_id}` с TTL 5 минут.

**`/delete_me_confirm`** в меню BotFather **не выводится** — только если вручную.

## 019. Админский канал в Telegram для алертов

**Решение:** отдельный приватный канал, бот шлёт туда:
- `#critical` — критические ошибки (БД, диск, webhook)
- `#anomaly` — аномалии (упавший WHOIS-сервер TLD, rate limit hits)
- `#daily` — ежедневная сводка

**Дедупликация** через Redis: `alert:{hash}` с TTL `Limits.alert_dedup_ttl_minutes` (дефолт 10 минут).

Hash считается от `(severity, title, details[:200])` — этого достаточно, чтобы одно и то же сообщение не зашло в канал десятки раз подряд.

**Нормы дедупликации (нормальная частота и severity):**
- `#critical` (🚨): редкие (1–2 в час при реальной проблеме). Дедуп предотвращает спам от повторяющихся ошибок в течение окна.
- `#anomaly` (⚠️): при всплесках (массовые WHOIS-фейлы, rate limit hits). Дедуп по заголовку + первым 200 символам деталей.
- `#info` (ℹ️): важные события (старт/стоп). Обычно 1 раз за окно.
- `#daily` (📊): ежедневная сводка. Дедуп по тексту (чтобы за один день не задвоилась).

**Sentry** — для трейсбеков, не дублирует канал.

Нормы описаны в `src/services/alerts.py` (реализация) и `MIGRATIONS.md` (связанные уроки). При изменении TTL — правь `Limits`.

## 023. WHOIS Server Overrides per TLD (DEPRECATED in v0.4.0)

> **DEPRECATED:** механизм `WHOIS_SERVER_OVERRIDES` удалён в v0.4.0 (Этап 10).
> Его роль играет WHOIS proxy gateway — см.
> [ADR 028](#028-whois-proxy-gateway-as-primary-lookup). Запись оставлена
> для истории, чтобы те, кто видел старый env-флаг, понимали почему его
> больше нет.

**Решение (историческое):** возможность переопределять WHOIS-сервер для конкретных TLD через переменную окружения `WHOIS_SERVER_OVERRIDES` (JSON-объект `{tld: server}`).

**Почему:**
- Дефолтные WHOIS-сервера регистраторов иногда недоступны с конкретных хостингов (блокировки, ACL, маршрутизация). Пример: `whois.tcinet.ru` для `.ru`/`.рф` блокируется с части провайдеров.
- Сообщество держит публичные зеркала (`whois.pinspb.ru` для `.ru`), которые отдают тот же протокол на 43 порту.
- Дешевле, чем поддержка proxy/SOCKS — просто другой адрес в конфиге, без изменений в коде.

**Приоритет источника сервера в `query_whois`:**
1. Явный параметр `server=...` (программное намерение, тесты)
2. `WHOIS_SERVER_OVERRIDES[tld]` (env-конфиг)
3. Встроенный `WHOIS_SERVERS[tld]` mapping
4. IANA discovery

**Пример:**
```
WHOIS_SERVER_OVERRIDES={"ru":"whois.pinspb.ru","xn--p1ai":"whois.pinspb.ru"}
```

Ключи приводятся к lowercase валидатором Settings, значения — строки.


## 024. Скрытая команда `/version` с build info

**Решение:** диагностическая команда `/version` существует, но НЕ выводится в меню BotFather и НЕ упоминается в `/help`. Минимальный вывод для всех, расширенный — только для `ADMIN_USER_IDS`.

**Почему скрыта:**
- Не загромождает меню для обычного юзера.
- Полезна почти исключительно в репорте бага («какая у тебя версия?» → «/version» → скриншот) или для админа при дебаге деплоя.
- Расширенный вывод утекает stack-версии (Postgres/Redis) — это нормально для open-source, но смысл показывать его в меню всем = ноль.

**Build info через `scripts/generate_build_info.sh`:**
- Скрипт пишет `src/_build_info.py` с commit/branch/tag/timestamp.
- Файл гитнорируется (каждая сборка — свой).
- Импорт ленивый с fallback на `"unknown"` если файл отсутствует (dev-режим).

**Альтернативы которые отклонили:**
- ARG в Dockerfile + `os.environ` — требует пересборки на каждое изменение и не доступно ARQ-воркеру без переменных env. Текущий вариант проще.
- Чтение `.git` из контейнера в рантайме — `.git/` не попадает в образ; добавлять его обратно — overhead и security-риск.


## 025. Search в `/list` через FSM-состояние и Redis-state

**Решение:** поиск по подстроке в `/list` запускается кнопкой `🔍 Поиск`, переводит в FSM `ListSearchStates.waiting_for_query`, после ввода сохраняет query в Redis `list_state:{user_id}` (TTL 30 мин). Filter и search-query сохраняются ВМЕСТЕ — пагинация prev/next корректно их подхватывает.

**Почему Redis-state, а не FSM-data:**
- FSM-data MemoryStorage умирает при рестарте бота — юзер видит сбросившийся фильтр без объяснений. Redis с TTL — устойчив к рестартам.
- В callback_data нельзя сохранять search-query из-за лимита 64 байта.
- HASH из двух полей (`f`, `q`) дёшев в Redis-памяти и быстр на pipeline.

**Почему сбрасываем по `/list`:**
- Команда «начать заново» — естественный UX. Если хочешь продолжить поиск — пользуешься пагинацией, а не повторно вводишь команду.

**Privacy:** сам search-query НЕ логируется в structlog в plaintext — только `query_len`. Это персональный интерес пользователя (какие домены он ищет → намерения по портфелю).


## 026. Wishlist как отдельный режим `user_domains` с одноразовым уведомлением

**Решение:** один булев флаг `user_domains.is_wishlist`. Wishlist-домен — обычная подписка с особым флагом, попадающая под отдельную ветку логики:
- `calculate_next_check(is_wishlist=True)` → фиксированные 24 часа.
- При переходе `is_registered=True → False` (только при наличии `old_data`) — enqueue `send_wishlist_available_notice`.
- Задача после успешной отправки DELETE'ит wishlist-подписку (одноразовость).

**Почему один флаг, а не отдельная таблица:**
- Quota — общая (`MAX_DOMAINS_PER_USER`), пользователю всё равно нужна одна шкала «у меня 50 интересных доменов, неважно — tracking или waiting».
- Все вспомогательные структуры (cache, диспетчер check_domain, alembic-схема) уже работают на доменном уровне — переиспользуем.

**Почему одноразовость (DELETE после уведомления):**
- Освободившийся домен — событие, не статус. Если пришло уведомление и пользователь его проигнорировал — повторять смысла нет (между уведомлениями домен может уже улететь).
- Если пользователь хочет «снова попробовать поймать тот же домен» — он делает `/wishlist <domain>` повторно. Это требует осознанного действия.

**Почему НЕ триггерим уведомление для первой проверки (old_data is None):**
- При добавлении уже-свободного домена в wishlist — это ошибка пользователя, не «событие». Лучше дождаться, пока домен реально кто-то заберёт и отпустит (или пока пользователь явно сделает `/whois example.com` и увидит «не зарегистрирован»).

**Подписки на смену регистратора/NS НЕ работают на wishlist-доменах:** при `add_to_wishlist` мы выключаем `notify_*` флаги. Это исключает дубль-уведомления «registered → free» через обычный change-notice пайплайн.


## 027. Однокомандный деплой через `scripts/deploy.sh`

### Контекст

Типовое обновление бота требует последовательного выполнения 5-6 шагов:
`git pull`, регенерация build info, `docker compose build`, `alembic upgrade head`, `docker compose up -d`, проверка healthcheck. Ручное выполнение каждый раз — источник ошибок: легко забыть регенерировать build info (в логах останется старый commit), пропустить миграцию (бот стартует, но падает на запросах), не дождаться healthy (тестируешь на ещё не готовом сервисе).

### Решение

`scripts/deploy.sh` выполняет полную последовательность с защитами:

- Отказ при dirty working tree — нельзя случайно потерять локальные изменения.
- Сохранение previous commit в `.last-deployed-commit` (gitignored) — заготовка под будущий rollback-скрипт.
- Healthcheck с таймаутом 30s — деплой не считается успешным, пока контейнеры не стали healthy.
- HTTP `/health` проверка — финальная гарантия что бот реально отвечает.
- Idempotent — повторный запуск без новых коммитов выходит на «Already up to date», не делает лишней работы.

### Альтернативы

**Полноценный CI/CD с auto-deploy при push в `main`.** Требует webhook на сервере, secrets management, более сложный rollback. Overkill для single-server setup и убирает возможность ручной валидации перед деплоем.

**Ansible playbook.** Промышленный стандарт для конфигурации серверов, но весь наш ops — это `docker compose` команды. Tooling непропорционален задаче.

**systemd unit + Renovate/Watchtower.** Watchtower уже работает на сервере для других контейнеров, но он автоматически обновляет образы без миграций БД и регенерации build info. Для нашего стека он бы вызывал проблемы.

### Дальнейшее развитие

Bash-скрипт без зависимостей, ~80 строк, читаемый и легко расширяемый:

- Rollback-скрипт через `.last-deployed-commit`.
- Алерт в admin-канал о начале/завершении деплоя.
- Slack/Telegram-уведомления о падении healthcheck.


## 028. WHOIS proxy gateway as primary lookup

### Контекст

ADR 023 (`WHOIS_SERVER_OVERRIDES`) решил частный случай — переключение на
`whois.nic.ru` для `.ru` с зарубежных хостеров где `tcinet.ru` заблокирован.
Но это не покрывало:

- Все `.ru`-домены (`whois.nic.ru` — thin WHOIS только для своих).
- Другие проблемные зоны (`.cn`, `.am`, `.in`, `.au` и т. п.).
- Кэширование (был user-level cache, не глобальный).
- RDAP-обработку (мы парсили JSON сами, дублируя работу).

### Решение

Развёрнут собственный WHOIS proxy gateway:

- На основном сервере: `127.0.0.1:43` (WHOIS-протокол), `127.0.0.1:8043`
  (HTTP/JSON).
- Сам выбирает upstream: WHOIS, RDAP, или RU-proxy (отдельный VDS в РФ
  для `.ru/.рф/.su`).
- Кэширует 24 ч (positive) и 10 мин (negative).
- Возвращает структурированный JSON с метаданными
  (`source`, `cached`, `fetched_at`, `ttl_remaining`).
- Healthcheck через `/healthz`.
- Прокси-сервис работает на хосте (не в Docker). Compose-сеть имеет
  фиксированную subnet `172.28.0.0/16`, чтобы `host.docker.internal`
  можно было захардкодить на её gateway (`172.28.0.1`). Magic-значение
  Docker'а `host-gateway` тут не подходит — оно резолвится в gateway
  default `docker0` (`172.17.0.1`), на котором наши compose-сервисы
  не сидят; пакет уходит «в никуда».
- На хосте требуется ufw allow для этой subnet:
  `ufw allow from 172.28.0.0/16 to any port 8043 proto tcp` — без него
  default `deny (incoming)` ufw блокирует входящий трафик `:8043`
  на интерфейсе compose-bridge. Внешний `eth0` остаётся под default-deny,
  публичной exposure не возникает.
- URL контейнеры читают из `WHOIS_PROXY_URL`
  (в проде — `http://host.docker.internal:8043`).

Бот теперь ходит ВСЕГДА в прокси через HTTP/JSON
(`src.whois.proxy_client.lookup_via_proxy`). При недоступности прокси —
fallback на `src.whois.client.lookup_direct` (прямой RDAP +
WHOIS:43 lookup, сохранённая страховка из Этапов 3 и 7a).

### Альтернативы

**Использовать прокси только для `.ru`** → не задействует RDAP-парсинг и
24h-кеш для остального.

**Полная миграция без fallback** → бот вообще не работает если прокси упал;
неприемлемо для single-server setup.

**Прямая зависимость на python-библиотеку RU-relay** → проблемы с
лицензиями / поддержкой; прокси даёт чистую сетевую границу.

### Следствия

- [ADR 023](#023-whois-server-overrides-per-tld-deprecated-in-v040)
  помечен DEPRECATED — функционал заменён прокси, env-флаг удалён.
- 24-часовой кеш на прокси: пользователь видит `fetched_at` в карточке,
  при `/check` или кнопке «Обновить» получает то же из proxy-cache.
  Принимаем; при жалобах попросим у proxy-команды добавить
  `?refresh=1` параметр.
- Новые значения `DataSource` в `WhoisData.source` для отличения путей:
  `proxy_rdap`, `proxy_whois`, `proxy_whois_ru`, `proxy_none` —
  оставляем `rdap`/`whois` для direct-пути.

### Мониторинг

ARQ cron `proxy_health_check` (каждые 15 минут) пингует `/healthz`
прокси; при падении — `AlertService.send_critical` в админ-канал.
Дедупликация AlertService подавит дубли в течение
`Limits.alert_dedup_ttl_minutes` (10 мин по умолчанию). Sentry получает
`warning` на каждый fallback на direct-lookup (через стандартное
structlog-логирование).


## 029. Per-domain notification settings — extended

### Контекст

В Этапе 5 ([ADR 012](#012-webhook-для-уведомлений-о-смене-статусов-закладываем-сразу))
была введена базовая per-domain настройка уведомлений:

- ``UserDomain.notify_days`` — override списка дней через SQL `COALESCE(ud.notify_days, u.notify_days)`
- ``UserDomain.notify_{expiry, registrar_change, ns_change, status_change}`` — 4 boolean'а

Этап 11 расширяет это:

- Появилось **уведомление о смене владельца** (Этап 8); раньше оно шло
  через mapping на ``notify_registrar_change`` — пользователь не мог
  отделить «смена регистратора» от «смена владельца».
- Появились **problem-notice** (Этап 4): отсутствовал отдельный toggle.
- Не было настоящего **kill-switch**: «мут» в карточке /list
  вычислялся как «все 4 toggle'а выключены» — невозможно было
  кратковременно замьютить с возвратом к прежним настройкам.
- Не было UI: настройки правились только через `/notify` / `/unnotify`
  командами с грубым all-or-nothing.

### Решение

Три новые колонки в ``user_domains``:

- ``is_muted`` (bool, default false) — kill-switch. При True гасит ВСЕ
  типы независимо от индивидуальных toggle'ов. При unmute индивидуальные
  настройки сохраняются (отсюда необходимость отдельного поля, а не
  computed «все типы выключены»).
- ``notify_registrant_change`` (bool, default true) — собственный toggle
  для смены владельца. Раньше шёл через ``notify_registrar_change``.
- ``notify_problem`` (bool, default true) — для уведомлений об ошибках
  проверки. Раньше эвристика «есть ли хоть один включённый notify_*».

Defaults подобраны так, чтобы для существующих пользователей **поведение
не изменилось**: ничего не замьючено, regis­trant/problem-уведомления
приходят как раньше. ``notify_ns_change`` остаётся default=false
([ADR 012](#012-webhook-для-уведомлений-о-смене-статусов-закладываем-сразу)).

**Inline-конфигуратор** ``⚙️ Уведомления`` в карточке /whois (только
для отслеживаемых доменов):

- 6 toggle'ов по одной кнопке на ряд (легче тапать на мобиле); тап
  переключает boolean и перерисовывает клавиатуру через
  ``edit_message_reply_markup`` (не плодим сообщения).
- «🔇 Заглушить всё» / «🔔 Снять заглушение» — переключает ``is_muted``,
  при этом текст сообщения тоже обновляется.
- «📅 Изменить дни предупреждений» — FSM ``NotifyDaysStates``. CSV-ввод
  с валидацией (1–365, не более 10 значений); ``/default`` сбрасывает
  override в NULL, ``/cancel`` возвращает к конфигуратору без изменений.

### Альтернативы

**Переименовать существующие колонки** в ``notify_change_*`` (consistency
с новыми) — отказались: downgrade-incompatible миграция, риск регрессий
во всех таски проверках; выигрыш чисто косметический.

**Единое JSONB-поле** ``notification_settings`` — отказались: усложняет
SQL-фильтрацию (нельзя использовать ``WHERE ud.notify_expiry = true`` в
``expiry_scheduler``), приходится тащить строки в Python.

**Computed «is_muted = all toggles off»** — текущее поведение Этапа 5.
Отказались, потому что не позволяет «временно замьютить и вернуться к
прежним настройкам» — после unmute пришлось бы помнить какие из 4
toggle'ов были включены.

### Следствия

- ADR 012 расширяется: теперь 6 toggle'ов + 1 kill-switch вместо 4.
- ``notify_changes._TYPE_MAP`` для ``registrant*`` ключей переключён с
  ``notify_registrar_change`` на новый ``notify_registrant_change``.
  Пользователи, отключившие registrar_change чтобы не получать
  «административные» уведомления, теперь получают registrant-уведомления
  отдельно (default True) — это считаем UX-улучшением, не регрессией.
- ``services/formatters._is_muted`` теперь читает поле ``is_muted``
  напрямую — это не computed.
- ``expiry_scheduler`` SQL получил дополнительный фильтр
  ``ud.is_muted = false``.

## 030. SSL/TLS-сертификаты как параллельная подсистема мониторинга

### Контекст

Этапы 1–11 покрывали мониторинг WHOIS-данных: истечение регистрации,
смена регистратора/NS/статусов/владельца. Но **истечение SSL-сертификата
ломает сайт так же фатально, как истечение домена** — и происходит
гораздо чаще: Let's Encrypt живёт 90 дней (а не год-три как WHOIS),
auto-renewal иногда падает (DNS-вызов недоступен, certbot сломался,
кончилось место на диске), и пользователь узнаёт об этом из жалоб
клиентов.

### Решение

Полностью **параллельная подсистема** к WHOIS: ничего не переиспользуем
в БД и тасках — слишком разная семантика (срок жизни на порядок короче,
другие источники сбоев, другие adaptive-интервалы). Подсистема
структурно отзеркаливает WHOIS-стек:

| WHOIS                            | SSL                                          |
|----------------------------------|----------------------------------------------|
| ``whois_cache``                  | ``ssl_cache`` (новая таблица, PK = ``domain``) |
| ``WhoisData`` / ``WhoisError``   | ``SSLCertificate`` / ``SSLError``            |
| ``whois.client.lookup_domain``   | ``ssl.client.fetch_certificate``             |
| ``whois.scheduler``              | ``ssl.scheduler`` (свои TTL-buckets)         |
| ``whois.diff.compute_diff``      | ``ssl.diff.compute_ssl_diff``                |
| ``tasks.check_domain``           | ``tasks.check_ssl``                          |
| ``tasks.scheduler.scheduler_tick`` | ``tasks.ssl_scheduler.ssl_scheduler_tick`` |
| ``tasks.expiry_scheduler``       | ``tasks.ssl_reminders_scheduler``            |
| ``tasks.send_reminders``         | ``tasks.send_ssl_reminder``                  |
| ``tasks.notify_changes``         | ``tasks.notify_ssl_changes``                 |

Per-domain настройки (на ``UserDomain``):

- ``track_ssl`` (bool, default **true**) — kill-switch на мониторинг
  целиком. False → домен не попадает в ``ssl_scheduler_tick``-выборку
  (экономим ресурсы и не плодим уведомлений). Opt-out по политике:
  пользователи, добавившие домены ДО Этапа 12, получают SSL-мониторинг
  по умолчанию.
- ``notify_ssl_expiry`` (bool, default true) — напоминания об
  истечении и became_unreachable/became_reachable.
- ``notify_ssl_change_issuer`` (bool, default true) — смена CA или
  ротация (issuer + not_after).
- ``notify_ssl_days_override`` (int[] | NULL) — собственный набор дней
  предупреждения. NULL → ``User.notify_ssl_days_before``
  (default ``{14,7,3,1}`` — SSL живёт сильно короче WHOIS).

### Технические инварианты

- **chain validation отключён** (``verify_mode=CERT_NONE``,
  ``check_hostname=False``). Мы парсим peer cert как есть, даже если он
  истёк / самоподписан / выдан недоверенным CA. Цель — мониторинг,
  не валидация TLS-доверия.
- **CONNECT_TIMEOUT=10s обязателен** — иначе медленный хост вешает
  worker.
- **``no_https`` ≠ unreachable** — DNS-фейл, no route to host и т.п.
  не считаются падением SSL, это валидное «у домена просто нет HTTPS».
  Уведомлений не шлём.
- **First fetch не триггерит change-уведомлений** (``compute_ssl_diff``
  возвращает пустой diff при ``old=None``). Это покрывает кейс «только
  что включили мониторинг» — иначе пользователь сразу получил бы
  фантомное «issuer changed».
- **``became_unreachable`` — это переход**, а не состояние. В diff
  проверяем ``old.is_reachable``, иначе на каждом retry'е приходил бы
  дубль уведомления.
- **``is_muted`` имеет приоритет** — kill-switch гасит и SSL-уведомления.
- **Сериализация fingerprint в hex** (str), не bytes — БД хранит
  ``CHAR(64)``.

### Adaptive TTL для SSL-проверок

Шкала отличается от WHOIS (см. ``src.ssl.scheduler``):

| Дней до истечения | Интервал |
|-------------------|----------|
| > 30              | 1 день   |
| 7 – 30            | 6 часов  |
| 1 – 7             | 1 час    |
| ≤ 0 / нет данных  | 4 часа   |

``fail_count ≥ 10`` фиксирует интервал в 24 часа — не долбим мёртвый
хост. Это короче чем у WHOIS: LE-сертификаты ротируются раз в 90 дней,
любая просадка частоты проверок повышает риск пропустить ротацию.

### Альтернативы

**Расширить ``whois_cache``** колонками ``ssl_*`` — отказались: разный
жизненный цикл (LE 90 дней vs WHOIS 1+ год), разные intervals, разные
источники сбоев. Сводить в одну таблицу = усложнение SQL без выигрыша.

**Использовать ``ssl.SSLContext`` через ``ssl.create_default_context``
с дефолтным CA-bundle** — отказались. У нас задача мониторинга, а не
проверки доверия. С дефолтным trust-store fetch падал бы на каждом
домене с истёкшим или самоподписанным сертификатом — а это как раз те
случаи, которые мы хотим показать пользователю.

**Опираться на сторонние API (sslmate, ssl-checker)** — отказались.
Зависимость от сервиса, rate limits, payable, не нужны нам для
прямого TLS-handshake'а на стандартном порту 443.

### Следствия

- ``UserDomain`` получил 4 новые колонки. ``User`` — одну
  (``notify_ssl_days_before``). Миграция ``20260517_ssl``
  (down_revision ``20260517_pernotif``).
- ARQ-воркер регистрирует 5 новых тасок + 2 новых cron-расписания
  (см. ``src.tasks.arq_config``). Cron `ssl_scheduler_tick` идёт по
  той же сетке что и WHOIS-scheduler — каждые 5 минут.
- ``/whois`` карточка дополнена SSL-блоком (``format_ssl_block``);
  при первой проверке домена ставится `check_ssl` без ожидания тика,
  чтобы карточка в следующем открытии уже показала сертификат.
- Конфигуратор уведомлений (``notify_config_keyboard``) расширен
  3 toggle'ами и отдельной кнопкой «Изменить дни SSL-предупреждений»
  с собственной FSM (``NotifySslDaysStates``) — UX-разделение,
  чтобы пользователь не путал WHOIS-дни и SSL-дни.
- Privacy: SSL-данные публичные (любой получит их тем же TLS-handshake),
  логируем без redaction-правил, в отличие от WHOIS-контактов.


## 031. Universal RIR/ASN lookup client (rir2localdb integration)

### Контекст

Для будущего DNS-мониторинга (v0.8, см. ``TODO.md``) нужна возможность
определять «какой ASN/организация владеет данным IP». WHOIS-прокси из
ADR 028 эту задачу не решает — он работает с доменными WHOIS-серверами,
не с RIR-данными по IP/ASN. Прямой WHOIS на RIR (RIPE, ARIN, APNIC,
LACNIC, AFRINIC) медленный (1–2 секунды на запрос) и имеет жёсткие
rate limits — батч-операции упрутся в throttling.

Параллельно с этим проектом разработан ``rir2localdb`` — отдельный
сервис, который ежедневно зеркалит публичные данные пяти RIR
(delegated-extended + RPSL bulk), парсит в PostgreSQL и отдаёт
whois-подобную информацию по IP и ASN через REST API. Развёрнут на
том же сервере, listen ``172.28.0.1:18000`` (gateway compose-сети
бота), v0.1.1 на момент написания ADR.

### Решение

В v0.7.0 добавлен **универсальный HTTP-клиент** к rir2localdb (модуль
``src/rir_client/``). Этап **инфраструктурный** — клиент никак не
используется в UI или мониторинге сам по себе. Применение — в v0.8
(DNS A/AAAA мониторинг с ASN-фильтрацией для устранения шума от CDN
round-robin).

**Структура модуля:**

- ``src/rir_client/types.py`` — pydantic-модели ответов
  (``IPAllocation``, ``ASNAllocation``, ``RIRStatus``, ``SyncRun``,
  ``Source``)
- ``src/rir_client/errors.py`` — ``RIRError`` (returned) и
  ``RIRUnreachable`` (raised) — двухуровневая модель ошибок
- ``src/rir_client/client.py`` — async HTTP функции на aiohttp
- ``src/rir_client/__init__.py`` — публичное API

**Публичный API:**

- ``lookup_ip(addr, *, include_rpsl=True, session=None)``
  → ``IPAllocation | RIRError``
- ``lookup_asn(num, *, include_rpsl=True, session=None)``
  → ``ASNAllocation | RIRError``
- ``healthcheck(*, session=None)`` → ``bool``
  (raises ``RIRUnreachable`` на network failure)
- ``get_status(*, session=None)`` → ``RIRStatus``
  (raises ``RIRUnreachable``)

**Settings (``src/config/settings.py``):**

- ``RIR2LOCALDB_ENABLED`` (default ``true``, kill-switch для maintenance)
- ``RIR2LOCALDB_URL`` (default ``http://host.docker.internal:18000``)
- ``RIR2LOCALDB_TIMEOUT_SECONDS`` (default ``5.0``)
- ``RIR2LOCALDB_CONNECT_TIMEOUT_SECONDS`` (default ``1.0``)

**Health monitoring:**

ARQ cron ``rir_health_check`` каждые 30 минут проверяет:

1. ``/v1/healthz`` отдаёт ``{"status":"ok"}``
2. ``latest_sync_run.started_at`` свежее ``MAX_SYNC_AGE`` (26 часов —
   покрывает суточный каденс + ~2h slack на randomized delays)
3. ``latest_sync_run.status == "success"``

Дедупликация alert'ов через ``AlertService`` (Redis-based, TTL из
``Limits.alert_dedup_ttl_minutes``). Поскольку текущий API
``AlertService.send_critical(title, details)`` дедуплицирует по
``(severity, title, details[:200])`` — каждый failure mode получил
собственную title-константу, чтобы соседние режимы не перетирали
друг друга в одном TTL-окне.

### Технические инварианты

- **Error policy — двухуровневая.** ``lookup_*`` возвращают
  ``RIRError`` (не raise) для предсказуемого pattern-matching у
  callers (``case RIRError(kind="not_found"): ...``). ``healthcheck``
  и ``get_status`` raise ``RIRUnreachable`` для использования в
  cron-задаче, где исключение идиоматичнее булевого сентинеля.
- **``ErrorKind`` — закрытый Literal**: ``unreachable``, ``not_found``,
  ``bad_request``, ``server_error``, ``invalid_response``, ``disabled``.
  Расширение списка — breaking change для callers с exhaustive
  match — оставляем на v0.8.
- **Session injection** — все 4 функции принимают
  ``session: aiohttp.ClientSession | None = None``. Если ``None`` —
  создаём и закрываем сами; если передана — caller владеет жизненным
  циклом. Тот же паттерн что и в ``proxy_client.py``.
- **RPSL block — untyped** (``dict[str, Any]``) в v0.7. rir2localdb
  v0.1.1 имеет known limitations: APNIC IANA-NETBLOCK placeholder'ы
  доминируют в RPSL для не-RIPE блоков, ARIN RPSL pending. Полная
  типизация оправдается в v0.8 когда DNS-мониторинг реально применит
  ``rpsl.organisation.org_name`` в карточке ``/whois``.
- **``ValidationError`` от pydantic → ``RIRError(invalid_response)``**.
  Это сигнал что rir2localdb выкатил несовместимый schema-bump —
  caller должен зафейлить операцию, а не пытаться приспособиться.

### Альтернативы

**Прямой WHOIS-сервер RIR через TCP:43.** Медленно (1-2 секунды на
IP), rate limits, не подходит для batch операций.

**Внешний сервис (Team Cymru, ipinfo.io).** Зависимость от внешнего
SaaS, бесплатные лимиты не покрывают наш профиль использования,
privacy considerations для пользовательских IP — отдавать наружу
IP'шники пользователей не хотим.

**Локальная база MaxMind GeoIP/ASN.** Требует регулярного обновления
+ лицензионных условий. rir2localdb даёт более полные данные
(allocation + RPSL) из публичных источников без лицензионных
ограничений.

**``httpx`` вместо ``aiohttp``.** Отказались для consistency с
``src/whois/proxy_client.py`` (ADR 028) — тот же async API, та же
накопленная экспертиза проекта.

### Следствия

- Один новый ADR (этот), один новый модуль ``src/rir_client/``,
  одна новая ARQ cron-задача (``src/tasks/rir_health.py``).
- ``src/tasks/arq_config.py`` — два новых импорта (по одному в
  ``_build_functions`` и ``_build_cron_jobs``), один новый ``cron(...)``
  блок (``minute={0, 30}``, ``run_at_startup=False``).
- Появляется поверхностная зависимость от внешнего HTTP-сервиса
  (rir2localdb), но при его недоступности lookup'ы возвращают
  ``RIRError(unreachable)``, не падают. Бот продолжает работать без
  ASN-данных.
- На хосте нужен ufw rule allow от ``172.28.0.0/16`` на порт ``18000``
  (зеркало правила #5 для ``8043`` из ADR 028) — добавлен системой
  перед этим этапом.
- Migration нет — etap инфраструктурный, schema не меняется.
- В v0.7 client нигде не используется — это намеренно. v0.8
  применит его для DNS monitoring (новая таблица ``dns_cache``, новые
  per-domain toggles, новый scheduler с ASN-aware фильтрацией).


## 032. DNS A/AAAA monitoring как параллельная подсистема

### Контекст

Этапы 1–13 покрывали мониторинг WHOIS (истечение регистрации, смена
регистратора/NS/статусов/владельца) и SSL-сертификатов. Но между
ними оставалось слепое пятно — **реальное состояние DNS-резолюции
домена**. WHOIS-NS показывает что в registry, но не показывает что
DNS отдаёт фактически. Сценарии, проходившие незамеченными:

- **Угон через смену DNS** — атакующий меняет NS на уровне DNS,
  registry-WHOIS ещё показывает старые NS какое-то время. Расхождение
  DNS-NS vs WHOIS-NS — классический ранний сигнал.
- **Domain takeover** — A-запись указывает на освобождённый IP
  облачного провайдера, который злоумышленник зарегистрировал на
  себя.
- **Падение DNS** — NS-сервера перестали отвечать, домен не
  резолвится, сайт недоступен. WHOIS этого не видит (регистрация
  ещё валидна).
- **Незавершённая миграция** — сменили хостинг, забыли обновить
  часть записей, домен резолвится непредсказуемо.

Параллельно в v0.7.0 (ADR 031) добавлен ``rir_client`` — он позволяет
определять ASN каждого IP, что в перспективе даёт ASN-фильтрацию шума
от CDN round-robin (Cloudflare и т. п. постоянно меняют IP в пределах
своего ASN — это не настоящее изменение хостинга).

### Решение

Полностью **параллельная подсистема** к WHOIS и SSL, по тем же
архитектурным паттернам что ADR 030 (SSL). Своя таблица ``dns_cache``,
свои cron-задачи, свой scheduler с собственными adaptive-интервалами.

| WHOIS | SSL | DNS |
| --- | --- | --- |
| ``whois_cache`` | ``ssl_cache`` | ``dns_cache`` |
| ``WhoisData``/``WhoisError`` | ``SSLCertificate``/``SSLError`` | ``DNSRecords``/``DNSError`` |
| ``whois.client`` | ``ssl.client.fetch_certificate`` | ``dns_monitor.resolve_records`` |
| ``whois.scheduler`` | ``ssl.scheduler`` | ``dns_monitor.scheduler`` |
| ``whois.diff`` | ``ssl.diff.compute_ssl_diff`` | ``dns_monitor.diff.compute_dns_diff`` |
| ``tasks.check_domain`` | ``tasks.check_ssl`` | ``tasks.check_dns`` |
| ``tasks.scheduler_tick`` | ``tasks.ssl_scheduler_tick`` | ``tasks.dns_scheduler_tick`` |
| ``tasks.notify_changes`` | ``tasks.notify_ssl_changes`` | ``tasks.notify_dns_changes`` |

DNS-резолвинг через **dnspython** (async resolver) с цепочкой external
резолверов (Cloudflare ``1.1.1.1`` + Google ``8.8.8.8``). При сбое
первого — fallback на следующий. Локальный unbound — future work для
v0.9.

Per-domain настройки (на ``UserDomain``):

- ``track_dns`` (bool, default true) — kill-switch на мониторинг
  целиком. False → домен не попадает в ``dns_scheduler_tick`` выборку.
- ``notify_dns_a_change`` / ``notify_dns_aaaa_change`` — смена
  A/AAAA-записей.
- ``notify_dns_ns_change`` — гибридный toggle: обычная смена NS
  (info) И расхождение DNS-NS vs WHOIS-NS (critical). Оба под одним
  переключателем, но с разным тоном/эмодзи в сообщении.
- ``notify_dns_unreachable`` — became_unreachable / became_reachable.

### Технические инварианты

- **First fetch не триггерит уведомлений** — ``compute_dns_diff(old=None)``
  возвращает пустой diff (тот же инвариант что WHOIS и SSL). Покрывает
  «только что включили мониторинг».
- **became_unreachable — переход, не состояние** — проверяем
  ``old.is_reachable``, иначе на каждом retry'е дубль.
- **``invalid_domain`` / ``disabled`` НЕ считаются как unreachable** —
  это конфигурационные проблемы, не сетевые (аналогия ``no_https``
  в SSL).
- **``is_muted`` имеет приоритет** — гасит и DNS-уведомления.
- **NS-mismatch — отдельный persistent state**
  (``dns_cache.ns_mismatch_active``) для transition detection
  (``detected``/``resolved``) и для adaptive TTL.
- **WHOIS-NS читается из колонки ``whois_cache.name_servers``**
  (отдельная ARRAY(Text), не из ``raw_data``) — для
  ``detect_ns_mismatch``.
- **Sort-нормализация при сравнении** — A/AAAA/NS списки сортируются
  перед diff, порядок не считается изменением.

### Adaptive TTL для DNS-проверок

В отличие от SSL (где интервал зависит от ``not_after``), у DNS нет
«истечения». Критерии (``src.dns_monitor.scheduler``):

| Условие | Интервал |
| --- | --- |
| ``ns_mismatch_active`` | 30 минут (critical state) |
| ``fail_count >= 10`` | 24 часа (backoff) |
| recent change < 24h, без ASN-смены | 6 часов (likely CDN) |
| recent change < 24h, с ASN-сменой | 1 час (true critical) |
| новый домен (no ``last_successful``) | 1 час |
| стабильный | 1 день |

### ASN-фильтрация (placeholder в v0.8.0)

rir2localdb v0.1.1 не отдаёт IP→ASN маппинг (endpoint ``/v1/ip/{addr}``
возвращает allocation, не ASN). Поэтому в v0.8.0 ``enrich_with_asn``
возвращает пустой list, ``asn_set`` всегда пустой, ``last_change_was_asn``
всегда False. ``compute_dns_diff`` работает без ASN-фильтра — любая
смена IP даёт ``a_changed=True`` (больше CDN-шума, но не пропускаем
реальные смены).

В v0.8.x — координация с владельцем rir2localdb на добавление
endpoint ``/v1/ip/{addr}/asn`` (через RPSL ``inetnum.origin``). После
этого ASN-фильтр активируется БЕЗ изменений в коде ``dns_monitor`` /
``check_dns``.

### Альтернативы

**Расширить ``ssl_cache`` или ``whois_cache`` колонками ``dns_*``.**
Отказались: разная семантика, разные источники сбоев, разные
интервалы. Сводить в одну таблицу = усложнение SQL без выигрыша
(тот же аргумент что в ADR 030).

**Прямой DNS:53 через сокеты без библиотеки.** Отказались: dnspython
зрелый, async из коробки, DNSSEC-ready для v0.9, обработка edge-cases
(truncation→TCP, EDNS) уже решена.

**Локальный unbound с самого начала.** Отложили в v0.9. В v0.8.0
external резолверы проще (нет system-level зависимости, нет нового
сервиса на хосте). Privacy-минус (DNS-запросы уходят к Cloudflare/
Google) приемлем — это публичные резолверы, и мы спрашиваем только
публичные домены.

**Внешний DNS API (Cloudflare Radar, DNS-over-HTTPS провайдеры).**
Отказались: зависимость от SaaS, rate limits, privacy. dnspython +
прямые UDP-запросы дешевле и под нашим контролем.

### Следствия

- ``UserDomain`` получил 5 новых колонок. Новая таблица ``dns_cache``
  (PK ``domain``, ~14 колонок). Миграция ``20260519_dns``
  (down_revision ``20260517_ssl``).
- ARQ-воркер регистрирует 3 новых таски (``check_dns``,
  ``dns_scheduler_tick``, ``send_dns_change_notice``) + 1 новый cron
  (``dns_scheduler_tick``, каждые 5 минут — та же сетка что WHOIS/SSL).
- ``/whois`` карточка дополнена DNS-блоком (``format_dns_block``); при
  первой проверке домена ставится ``check_dns`` без ожидания тика.
- Конфигуратор уведомлений расширен 5 DNS-toggle'ами (итого 14
  toggle'ов).
- Новая зависимость ``dnspython >= 2.6, < 3``.
- Privacy: DNS-данные публичные (любой резолвер их отдаёт), логируем
  без redaction (аналогия SSL).

### Out of scope для v0.8.0

- **DNSSEC валидация** — future work v0.9 (требует валидирующий
  резолвер, обработка bogus/indeterminate). В v0.8 мы мониторим
  записи, не проверяем DNSSEC-цепочку (та же философия «мониторим,
  не валидируем» что в SSL ADR 030).
- **Локальный unbound** — v0.9 (для приватности и кэширования).
- **Полноценная ASN-сборка** — v0.8.x (зависит от rir2localdb upgrade).
- **Adaptive CDN learning** — v0.8.x (детект «этот домен всегда меняет
  IP в пределах ASN X» после 30 дней наблюдения, чтобы ещё агрессивнее
  подавлять шум).
- **``dns_reminders_scheduler``** — не нужен, у DNS нет «истечения»,
  реактивных уведомлений из diff-цикла достаточно.


## 033. FSM-flow для команд без обязательного аргумента

### Контекст

Команды ``/add``, ``/rmv``, ``/check``, ``/notify``, ``/unnotify`` без
аргумента отвечали сухим ``errors.no_domain`` («Укажите домен. Пример:
/whois example.com»). Этого недостаточно для пользователей, которые
приходят из меню BotFather или просто тапают по команде — они не
понимают, что нужно ввести и куда.

Отзывы из real-world Telegram-тестирования и из переписки в чате
поддержки повторяются: «нажал /add, ничего не происходит, бот ругается»,
«у меня нет привычки писать команду с пробелом». Сухая ошибка — особенно
жёсткий fail для mobile UX, где набирать "/add " пробелом неудобно.

``/whois`` от этой проблемы не страдает: голый домен в чате уже
обрабатывается ``text``-роутером (общий plain-text handler), который
извлекает домен из произвольной строки и показывает карточку.

``/wishlist`` без аргумента ИМЕЕТ осмысленное поведение — показывает
список wishlist-доменов (см. ADR 026). FSM-flow его не затрагивает: с
аргументом — добавляет домен, без аргумента — показывает список (в
v0.7.1 эта функция была случайно сломана, восстановлена в v0.7.2).

### Решение

Ввести FSM-flow ``AwaitingDomainArg.waiting`` для **5 команд** с
обязательным доменом-аргументом (``/add``, ``/rmv``, ``/check``,
``/notify``, ``/unnotify``). Когда команда приходит без args:

1. Бот ставит state ``AwaitingDomainArg.waiting``, кладёт ``cmd`` в
   FSM-data и пишет prompt: «Введите домен для /{cmd}. /cancel — отмена.»
2. Пользователь шлёт следующее сообщение (не команда). Бот валидирует
   ввод через ``bot/validators.py``:
   - 0 доменов найдено → пишет «не похоже на домен, попробуйте ещё раз
     или /cancel». State остаётся.
   - 1 домен → бот показывает confirm «Выполнить /{cmd} {domain}?» с
     inline-кнопками **✅ Да / ❌ Нет**.
   - >1 домена → берёт первый, пишет «Нашёл несколько, возьму первый:
     ..., для массового импорта — /download». Тоже confirm.
3. На «Да» — выполняет ту же бизнес-логику, что и
   inline-форма ``/<cmd> <domain>`` (один и тот же
   ``DomainService``-метод / handler). На «Нет» — пишет «Отменено»,
   чистит state.

**Storage** — `MemoryStorage` (текущая реализация). State теряется
при рестарте бота — приемлемо для коротких подтверждений (~секунды).
Миграция на `RedisStorage` со встроенным TTL запланирована в v0.8.x
(см. TODO.md, раздел Tech debt).

**TTL state'а** обеспечивается middleware `clear_state_on_command`:
любая команда (`/...`), пришедшая в состоянии `AwaitingDomainArg.waiting`,
сбрасывает state до роутинга. Реального time-based TTL нет (это
ограничение MemoryStorage). На практике пользователь либо подтверждает
confirm-кнопкой в течение секунд, либо шлёт следующую команду — оба
случая корректны.

### Технические инварианты

- **Один FSM-state на все 5 команд.** ``cmd`` хранится в FSM-data, не
  в state-name — это даёт единый callback handler и единое поле для
  middleware-очистки. Альтернатива (отдельный state на каждую команду)
  требовала бы 5 копий handler'а и 5 веток в callback'е без выигрыша.
- **Token-карта в FSM-data.** ``callback_data`` ограничена 64 байтами
  Telegram-API, длинный домен туда не влезет. Поэтому генерируем
  ``uuid.uuid4().hex[:8]`` и кладём ``{token: domain}`` в FSM-data,
  callback несёт только токен. Карта — словарь, потому что пользователь
  может несколько раз ввести разные домены до подтверждения; старые
  токены тогда устаревают, но не падают (см. stale-обработку).
- **Stale-callback не падает.** Если token не найден в карте (state
  сброшен middleware'ом, пользователь начал заново, бот рестартовал
  на MemoryStorage) — callback редактирует сообщение в «Уже не
  актуально» и возвращается без exception'а. ``query.answer()`` всегда
  вызывается, чтобы убрать spinner.
- **State-cleanup через middleware, а не TTL.** Middleware
  ``clear_state_on_command`` проверяет: если ``message.text``
  начинается с ``/`` и текущий state — ``AwaitingDomainArg.waiting``,
  state очищается ДО routing'а. Без этого ``/list`` в state'е
  ушёл бы в FSM-text-handler как «домен», и пользователь застрял бы.
  Это же гарантирует выход из state'а — пользователь либо подтверждает,
  либо шлёт любую команду. Time-based TTL подключим при миграции на
  RedisStorage (см. Followup).
- **Privacy.** Введённый домен попадает только в исходящие сообщения
  бота (confirm + executing) и в БД через тот же путь, что обычный
  ``/add example.com``. В INFO-логи structlog plain-text сообщения
  пользователя не пишутся (это та же гарантия, что для search-query
  из ADR 025).
- **/whois и /wishlist НЕ в списке.** Голый домен уже работает через
  общий text-handler — `/whois` дублировать не нужно. У `/wishlist`
  пустой аргумент уже занят показом списка, FSM-prompt сломал бы это.

### Альтернативы

**Расширить ``errors.no_domain`` подсказкой «отправьте домен следующим
сообщением, я пойму».** Без FSM — следующее сообщение всё равно
обрабатывается ``text``-роутером с эвристикой extract_domain. Это
сработает для ``/add`` и ``/check`` (попадёт в карточку /whois,
пользователь нажмёт «👁 Следить») — но для ``/rmv``, ``/notify``,
``/unnotify`` это даст неверную команду. FSM привязывает ввод именно
к запрошенной команде.

**Отдельный state на каждую команду.** Дороже в коде, идентичен по
поведению. Один state с ``cmd`` в FSM-data покрывает все 5 случаев
одним callback-handler'ом.

**Полный отказ от inline-формы.** «Всегда спрашивать домен через
prompt». Сломал бы привычку power-users, которые шлют
``/add example.com`` одной строкой. Старый путь сохраняем — FSM
запускается только если ``command.args`` пуст.

### Следствия

- Новый state ``AwaitingDomainArg.waiting`` (``src/bot/states.py``).
- Новый handler ``src/bot/handlers/awaiting_arg.py`` с FSM-text- и
  callback-handler'ами, диспетчером ``cmd → callable``.
- Новая клавиатура ``cmd_arg_confirm_kb`` + ``CmdArgCallback``
  CallbackData в ``src/bot/keyboards.py``.
- Новый middleware ``clear_state_on_command`` (``src/bot/middlewares/``).
- 3 файла handler'ов (``add_remove``, ``check``, ``notifications``)
  перепаяны: вместо ``errors.no_domain`` ставят state.
- ~9 новых locale-ключей в ``commands.cmd_arg.*`` (RU + EN).
- Migration нет.

### Followup (v0.8.x)

Миграция всех FSM-states проекта (`AwaitingDomainArg`,
`ListSearchStates`, `NotifyDaysStates`, `NotifySslDaysStates`,
`DownloadStates`, `SettingsStates`) с `MemoryStorage` на
`RedisStorage(state_ttl=300)`. Это даст:
- устойчивость state'а к рестарту бота;
- реальный time-based TTL вместо middleware-clear;
- единое место хранения FSM-данных рядом с другими Redis-state'ами
  (`list_state:{user_id}`, `delete_pending:{user_id}`).

Отложено из v0.7.x, потому что затрагивает 6 state-классов и
требует отдельной проверки каждого на корректность сериализации.

## 034. Wishlist ↔ tracking — единая таблица, авто-промоут

### Контекст

Wishlist (ADR 026) и обычное отслеживание живут в одной таблице
``user_domains``, различаясь флагом ``is_wishlist``. В проде вскрылся
баг: домен, добавленный в wishlist, не виден в ``/list`` и не
переводится в отслеживание — ``/add`` отвечает «уже отслеживается», но
домен нигде не показывается.

Корень: ``DomainService.add_for_user`` проверяет
``DomainRepository.exists()``, которая **не различает** ``is_wishlist``.
Для wishlist-строки возвращает ``already_tracked`` и не снимает флаг.
При этом ``list_with_whois_filtered`` с ``include_wishlist=False``
(дефолт ``/list``) такие строки прячет. Домен застревает в лимбо:
невидим в обоих UX и не конвертируется. Тот же дефект бьёт по кнопке
``track`` из wishlist-уведомления (``on_wishlist_action`` →
``add_for_user``).

### Решение

``/add`` на домен, лежащий в wishlist, **тихо конвертирует** его в
обычное отслеживание (промоут). Разделы ``/list`` и ``/wishlist``
остаются строго раздельными — никаких бейджей в ``/list``.

- Новый метод ``DomainRepository.promote_from_wishlist(user_id, domain)``:
  один ``UPDATE ... WHERE is_wishlist=True`` → ``is_wishlist=False`` +
  восстановление дефолтов ``DEFAULT_NOTIFICATION_FLAGS``. SSL/DNS-toggle'ы
  не трогаем (``add_to_wishlist`` их не гасит).
- ``add_for_user`` читает строку через ``get_for_user`` вместо
  ``exists``: None → вставка; wishlist → промоут (новый статус
  ``promoted``); обычная tracked → ``already_tracked`` как раньше.

### Технические инварианты

- Промоут идемпотентен: повторный ``/add`` → ``already_tracked``.
- После промоута домен виден в ``/list`` (filter ``all``) и не виден в
  ``/wishlist``.
- Лимит ``max_domains_per_user`` при промоуте не пересчитывается
  (строка уже учтена).

### Альтернативы

- Показывать wishlist-домены в ``/list`` со значком — отвергнуто:
  смешивает две разные модели наблюдения, усложняет фильтры/статистику.
- Запретить ``/add`` для wishlist-домена с подсказкой «снимите из
  wishlist» — отвергнуто: лишний ручной шаг, плохой UX.

### Следствия

- Релиз v0.8.1 (багфикс, без миграций).
- Исполнение — TASK-0001.

## 035. Public Suffix List и поддомены (WHOIS у родителя, DNS/SSL у поддомена)

### Контекст

Валидатор доменов (``bot/validators.py``) чисто синтаксический, PSL
(Public Suffix List) в проекте нет. ``/add a.pinbetting.ru`` уходит в
WHOIS по полному поддомену, тот отдаёт «not found» → бот рапортует
«домен свободен», хотя registrable-домен ``pinbetting.ru`` занят. Также
нет разделения «юзерских» уровней 3–4 (``a.pinbetting.ru``) от публичных
зон, которые продают домены и имеют свой WHOIS (``org.uk``, ``co.uk``,
``com.br`` и т.п.).

Для администраторов слежение за DNS и SSL **именно поддомена** —
ценная функция (смена A/AAAA/NS, ротация сертификата на поддомене).

### Решение

- **WHOIS/expiry** берётся по **registrable-домену** (eTLD+1).
- **DNS (A/AAAA/NS) и SSL** — по самому **поддомену**.
- Источник PSL — библиотека **tldextract** (встроенный снапшот PSL).
  Разделение юзерских поддоменов от публичных зон отдаётся PSL:
  ``registrable_domain("a.pinbetting.ru") == "pinbetting.ru"``,
  ``registrable_domain("foo.org.uk") == "foo.org.uk"``.
- **Оффлайн-режим PSL:** tldextract инициализируется с bundled snapshot
  и **без сетевого автофетча** — парс домена должен быть синхронным и не
  ходить в сеть в горячем пути. Обновление PSL — через CI/ручной PR.
- ``include_psl_private_domains=False`` — private-секция PSL
  (``blogspot.com`` и пр.) не считается суффиксом; registrable
  определяется по ICANN-секции (как у регистратора).
- Чистый модуль ``src/utils/domains.py``: ``registrable_domain``,
  ``is_subdomain``, ``is_public_suffix_only``, ``split_domain``.
- Схема ``user_domains``: колонки ``registrable_domain`` (eTLD+1, индекс)
  и ``is_subdomain``. WHOIS-джойны/scheduler переключаются на
  ``registrable_domain``; ``dns_cache``/``ssl_cache`` остаются keyed по
  ``domain`` (поддомену). Несколько поддоменов одного родителя делят
  один ``whois_cache``-row (модель общего кэша, ADR 006, сохраняется).

### Технические инварианты

- ``a.pinbetting.ru`` при занятом ``pinbetting.ru`` НЕ показывается как
  «свободен»; карточка WHOIS — родителя, с баннером «это поддомен X».
- DNS/SSL поддомена резолвятся по самому поддомену.
- Ввод чистого публичного суффикса (``co.uk``) → ``invalid_domain``.
- tldextract парсит без сетевого вызова (тест на отсутствие сети).
- Backfill миграции: для существующих строк ``registrable_domain=domain``,
  ``is_subdomain=false`` (проверить, что поддоменов в проде нет).

### Альтернативы

- Хранить registrable в отдельной таблице — избыточно, eTLD+1
  детерминированно вычисляется из ``domain``.
- Вендорить ``public_suffix_list.dat`` и парсить самим — отвергнуто в
  пользу tldextract (меньше своего кода, проверенный парсер); сетевой
  автофетч отключаем явно.
- Свой минимальный список зон 3-го уровня — не покрывает тысячи
  многоуровневых зон, требует ручного сопровождения.

### Следствия

- Релиз v0.9.0, есть миграция БД → идёт после стабильного v0.8.1.
- Новая зависимость ``tldextract>=5,<6`` (+ ``uv.lock``).
- Исполнение — TASK-0002…0005, аудит — TASK-0006.
- Открывает дорогу ADR 036 (subdomain enumeration, MX/SPF/DKIM/DMARC).

## 036. Email/policy-записи: MX/SPF/DKIM/DMARC как параллельная подсистема (v0.10)

### Контекст

После ADR 035 (PSL/поддомены) бот наблюдает домен по четырём осям: WHOIS,
SSL, DNS (A/AAAA/NS), RIR/ASN. Для владельцев доменов и админов следующий
по ценности слой — почтовая инфраструктура и политики: ``MX`` (куда
доставляется почта), ``SPF`` (TXT, кто вправе слать от имени домена),
``DMARC`` (``_dmarc.<domain>`` TXT, политика обработки спуфинга) и ``DKIM``
(``<selector>._domainkey.<domain>`` TXT, подписи). Их изменение/ослабление
— частый признак мисконфигурации, компрометации или забытой миграции почты.

Подсистема DNS (ADR 032) уже резолвит ``A/AAAA/NS`` через ``dnspython``.
``MX`` и ``TXT`` — те же DNS-запросы, но с собственной семантикой парсинга и
диагностики, отличной от A/AAAA/NS.

### Решение (объём v0.10)

- **Объём v0.10 — только email/policy-записи.** Subdomain enumeration
  вынесен в отдельный этап **v0.11** (см. «Следствия»).
- **Сбор + базовая диагностика** (не полный аудит-движок):
  - ``MX``: список хостов с приоритетами; флаг «почта не настроена» (нет MX).
  - ``SPF`` (TXT на apex): наличие; режим ``-all`` / ``~all`` / ``?all`` /
    ``+all``; флаг нарушения RFC при >1 SPF-записи. Рекурсивный разбор
    ``include:`` **не** делаем (отложено).
  - ``DMARC`` (TXT на ``_dmarc.<domain>``): наличие; политика
    ``p=none|quarantine|reject``; ``sp`` / ``pct`` если заданы.
  - ``DKIM``: пробуем **ограниченный набор распространённых селекторов**
    (``default``, ``google``, ``selector1``, ``selector2``, ``k1``, ``mail``)
    — известное ограничение, без знания селектора DKIM не обнаружить
    генерически (фиксируем как ограничение, не как баг).
- **Параллельная подсистема** (как SSL ADR 030 и DNS ADR 032): своя таблица
  ``email_intel_cache`` (keyed по ``domain``, т.е. по самому домену/поддомену
  — ADR 035: записи берутся у запрошенного домена, не у registrable-родителя),
  свои ARQ-задачи и scheduler с собственным TTL (по DNS-TTL записей, в
  диапазоне как у DNS-подсистемы).
- **Уведомления per-domain** в стиле ADR 029: toggle'ы ``track_email`` и
  ``notify_email_change`` на ``UserDomain``; ``is_muted`` гасит и их.
  Diff считается как в WHOIS/SSL/DNS (новые значения vs предыдущие); шлём при
  значимых изменениях (смена/исчезновение MX, ослабление SPF ``-all``→``~all``,
  ослабление/снятие DMARC-политики, появление/пропажа DKIM-селектора).
- **Async-only**: резолв через ``dnspython`` (уже в зависимостях) в ARQ-тасках,
  без блокировок event loop.
- **UX**: отдельный блок в карточке ``/whois`` (после DNS/SSL); inline-toggle в
  ``⚙️ Уведомления``; все тексты — через локали ``ru``/``en``.

### Технические инварианты (защитить тестами)

- Парсеры ``SPF``/``DMARC``/``MX`` — чистые функции, покрыты юнит-тестами на
  edge-кейсах (нет записи, несколько SPF, ``include`` без рекурсии, regptr,
  кириллические/IDN-домены через punycode).
- ``compute_email_diff(old=None, ...)`` → пустой diff (как в SSL ADR 030).
- Отсутствие записи (нет SPF/DMARC) — валидное состояние, не «ошибка».
- DNS-фейл (NXDOMAIN/timeout) ≠ «политики удалены»: только переход
  reachable→unreachable шлёт уведомление, не повтор.
- ``is_muted`` гасит email-уведомления.
- Миграция ``email_intel_cache`` применяется на чистой БД и обратима;
  покрыта smoke-тестом миграций (TASK-0009).

### Альтернативы

- **Расширить ``dns_cache``** под MX/TXT — отвергнуто: у email-intel свой
  набор разобранных/диагностических полей и своя семантика diff; параллельная
  таблица (как SSL/DNS) чище и не раздувает DNS-схему.
- **Полный аудит-движок** (рекурсивный разбор SPF ``include`` с лимитом 10
  DNS-lookups, скоринг, рекомендации) — отложено в отдельный ADR; в v0.10
  только базовая диагностика.
- **DKIM по всем возможным селекторам / zone-walk** — невозможно генерически;
  оставляем пробинг распространённых селекторов как практичный компромисс.
- **Subdomain enumeration в v0.10** — отложено в v0.11; источник —
  **CT-логи (crt.sh)**, бесплатно и пассивно (без платных API, согласно
  CLAUDE.md). Будет оформлено отдельным ADR 037.

### Следствия

- Релиз **v0.10.0**, есть миграция БД (``email_intel_cache`` + toggle'ы на
  ``user_domains``).
- Новых внешних зависимостей нет (``dnspython`` уже есть).
- Исполнение — TASK-0015…0018 (схема → сбор/парсеры → ARQ/scheduler → UX).
- Открывает дорогу **ADR 037** (subdomain enumeration через CT-логи, v0.11).

## 037. Subdomain enumeration через CT-логи (on-demand, v0.11)

### Контекст

ADR 035 дал работу с поддоменами (registrable vs subdomain), но обнаружение
существующих поддоменов домена — отдельная ценность: для админа это карта
поверхности (shadow IT, забытые стенды, кандидаты на угон). Вынесено из ADR 036
в самостоятельный этап.

### Решение (объём v0.11 — только on-demand)

- **Источник — CT-логи через crt.sh** (бесплатно, пассивно, без платных API и
  без брутфорса; согласовано в ADR 036). HTTP-запрос
  ``https://crt.sh/?q=%25.<registrable>&output=json``.
- **On-demand команда** ``/subdomains <domain>``: разовый запрос (по registrable
  через ADR 035), результат — **read-only список** найденных поддоменов с
  **opt-in**: пользователь сам выбирает, какие взять на отслеживание (кнопки →
  переиспользуем существующий ``/add``-путь, ADR 035/034). **Авто-добавления
  нет** (защита лимита 50k, ADR 011, и WHOIS/DNS/SSL-нагрузки).
- **Периодический мониторинг с алертом «новый поддомен» — НЕ в v0.11**, вынесен
  в v0.12 (будущий ADR 038): фоновое отслеживание + уведомление как security-
  сигнал.
- **Кэш результатов** в таблице ``subdomain_enum_cache`` (keyed по registrable,
  TTL), чтобы повторные вызовы не били crt.sh. Запрос идёт **через ARQ-задачу**
  (crt.sh бывает медленным): хэндлер отвечает «ищу…», задача присылает список.
- **Graceful degradation**: crt.sh недоступен/таймаут/rate-limit → сообщение
  «временно недоступно», без падения хэндлера; ошибка — в админ-канал (ADR 019).
- **Нормализация выдачи**: lowercase, punycode (``idna``), dedup, отбросить
  wildcard-записи (``*.example.com``) и сам registrable; оставить только
  поддомены запрошенного registrable (PSL, ADR 035).

### Технические инварианты (защитить тестами)

- Парсер crt.sh-ответа — чистая функция, юнит-тесты: dedup, wildcard-фильтр,
  IDN/punycode, мусорный JSON, пустой ответ.
- crt.sh-клиент async, без блокировок loop; запрос изолирован в ARQ-задаче.
- crt.sh-недоступность ≠ падение: возвращаем «временно недоступно».
- Opt-in идёт через существующий ``/add`` (лимит 50k соблюдён); авто-добавления
  нет.
- Кэш per-registrable с TTL; повторный ``/subdomains`` в окне TTL не бьёт crt.sh.
- Миграция ``subdomain_enum_cache`` применяется на Postgres и обратима
  (smoke-тест TASK-0009).

### Альтернативы

- **Брутфорс по словарю** — шумно, нагрузка на DNS, неполно; отвергнуто
  (можно как доп.источник позже).
- **Пассивный DNS через сторонние API** — обычно платно/лимитировано, против
  конвенции (ADR 010); отвергнуто.
- **Авто-добавление найденного** — риск взрыва портфеля и упора в лимит 50k;
  отвергнуто в пользу opt-in.
- **Синхронный вызов crt.sh в хэндлере** — crt.sh медленный/нестабильный,
  блокировал бы ответ; делаем через ARQ.

### Следствия

- Релиз **v0.11.0**, есть миграция (``subdomain_enum_cache``).
- Новых внешних зависимостей нет (HTTP через ``aiohttp``, уже есть).
- Исполнение — TASK-0022…0024 (схема → crt.sh-клиент/парсер → UX-команда + opt-in).
- Открывает дорогу **ADR 038** (периодический мониторинг новых поддоменов +
  алерты, v0.12).

## 038. Периодический мониторинг новых поддоменов + алерты (v0.12)

**Статус:** принято. Преемник ADR 037 (on-demand enumeration), поверх
`subdomain_enum_cache`, по образцу SSL/DNS-подсистем (ADR 030/032).

### Контекст

ADR 037 дал разовый `/subdomains` (on-demand, read-only, opt-in). Но главная
ценность для безопасности — заметить **появление нового поддомена** между
проверками: shadow IT, забытый стенд, признак компрометации/угона. Нужен
фоновый мониторинг с уведомлением, как уже сделано для SSL/DNS.

### Решение

- **Opt-in per-domain.** Новый toggle `UserDomain.track_subdomains`
  (**default `false`** — в отличие от `track_ssl/dns/email`, которые `true`):
  enumeration бьёт crt.sh и шумит, поэтому включается явно. `is_muted` гасит и
  эти уведомления (ADR 029).
- **Сигнал — новые И исчезнувшие поддомены.** Два toggle'а:
  `notify_subdomain_new` (default `true`) и `notify_subdomain_removed`
  (default `true`). Исчезновение из CT-логов — слабее как сигнал, но полезно
  для инвентаря; оставляем отключаемым.
- **Частота — настраиваемо per-user.** `User.subdomain_check_interval_days`
  (per-user default, `server_default 7`) + опциональный per-domain override
  `UserDomain.subdomain_check_interval_override` (`NULL` → берём из User; паттерн
  `notify_ssl_days_override`, ADR 030).
- **Реконсиляция shared-cache vs per-user.** `subdomain_enum_cache` — общий per
  registrable (ADR 037), а интервал — per-user. Scheduler ставит `next_check_at`
  per registrable = `now + min(интервалов подписчиков)` (floor 1 день), с
  adaptive-backoff при фейлах crt.sh (расширяем `calculate_next_subdomain_check`).
  Самый «частый» подписчик задаёт темп, остальные получают тот же свежий кэш.
- **Scheduler — по образцу `ssl_scheduler_tick`** (ADR 030): cron-тик →
  bootstrap (registrable с ≥1 подписчиком `track_subdomains=true` без записи в
  кэше → заглушка `next_check_at=now()`, `ON CONFLICT DO NOTHING`) → выборка due
  по подписчикам (`track_subdomains=true AND is_muted=false`) → enqueue
  `check_subdomains` (self-guard флагом `subdomain_check_in_progress` уже есть).
- **Diff + baseline.** Чистая функция `compute_subdomain_diff(old, new)` →
  `{new: [...], removed: [...]}`. **`old=None` → пустой diff** (первая
  enumeration — baseline, НЕ алертим; инвариант как `compute_ssl_diff(old=None)`,
  ADR 030). `check_subdomains` на каждом refresh сравнивает новый список со
  старым из кэша ДО перезаписи; при изменениях enqueue `notify_subdomain_changes`.
- **Уведомления — fan-out.** `notify_subdomain_changes` рассылает всем
  подписчикам registrable с `track_subdomains=true`, honoring
  `notify_subdomain_new`/`notify_subdomain_removed` и `is_muted`. Текст —
  security-стиль: «🆕 новый поддомен X у domain» / «➖ исчез поддомен Y».
- **UX.** Toggle'ы в inline-конфигураторе `⚙️ Уведомления` карточки `/whois`
  (`track_subdomains`, `notify_subdomain_new`, `notify_subdomain_removed`) +
  кнопка-FSM для интервала (по образцу `edit_ssl_days`, ADR 029). Все строки —
  локали ru/en (инвариант `test_all_ru_keys_present_in_en`).

### Технические инварианты (защитить тестами)

- `compute_subdomain_diff(old=None, …)` → пустой diff (нет алерта на baseline).
- Diff игнорирует порядок/дубликаты, работает на нормализованных списках
  (lowercase/punycode из ADR 037).
- Scheduler берёт только подписчиков `track_subdomains=true AND is_muted=false`;
  `track_subdomains=false` исключает из мониторинга.
- `next_check_at` per registrable = `now + min(интервалов)` (floor 1 день);
  backoff при фейлах не сбрасывается некорректно успехом другого подписчика.
- Fan-out не дублирует уведомление одному пользователю; honoring per-domain
  toggle'ов и `is_muted`.
- Миграция (toggles + interval-поля) применяется на Postgres и обратима
  (smoke-тест TASK-0009).
- Anti-drift: сигнатуры/поля — со `spec`/`autospec` в тестах (CLAUDE.md).

### Альтернативы

- **Авто-`track_subdomains=true` для всех** — нагрузка на crt.sh + шум; отвергнуто
  в пользу явного opt-in (default `false`).
- **Фиксированный глобальный интервал** — не учитывает разные потребности;
  выбран per-user.
- **Отдельная таблица под мониторинг** — избыточно: `subdomain_enum_cache`
  (ADR 037) уже keyed per registrable с `next_check_at`/`fetched_at`; переиспользуем.
- **Diff per-user** — набор поддоменов общий per registrable; diff естественно
  per-registrable с fan-out подписчикам.

### Следствия

- Релиз **v0.12.0**, есть миграция (toggles + `subdomain_check_interval_*`).
- Новых внешних зависимостей нет.
- Исполнение — TASK-0027 (схема) → 0028 (diff + scheduler) → 0029 (уведомления +
  UX) → 0030 (комплексный аудит v0.12).
- Закрывает дорожную карту subdomain enumeration (ADR 037 + 038).

## 039. Wishlist и tracking — независимые списки (отдельная таблица, v0.11.1)

### Контекст

После релиза пришли негативные отзывы, ручная проверка подтвердила два
UX-дефекта в wishlist:

1. **Домен пропадает из `/list` при добавлении в wishlist.** `user_domains`
   несёт один флаг `is_wishlist` при `UNIQUE(user_id, domain)` — значит одна
   пара (пользователь, домен) — это **одна строка**, которая либо tracked
   (`is_wishlist=False`), либо wishlist (`True`). `DomainRepository.add_to_wishlist`
   делает UPSERT с `on_conflict_do_update`, который переводит существующую
   tracked-строку в `is_wishlist=True` (и гасит `notify_*`). `/list`
   (`list_with_whois_filtered`, `include_wishlist=False`) фильтрует
   `is_wishlist.is_(False)` — домен молча исчезает из портфеля.
2. **Из wishlist нельзя убрать домен из карточки `/whois`.** У слежения есть
   парная кнопка follow/unfollow, у wishlist — только «🎯 Хочу когда
   освободится» (`whois_actions(show_wishlist=...)`), а `unwishlist`-действия и
   проверки членства в wishlist в карточке нет (метод `remove_wishlist` в
   репозитории существует, но не имеет точки входа из UI).

ADR 034 закрыл только обратное направление (`/add` на wishlist-домен → тихий
промоут в tracked). Корень в том, что **модель в принципе не может выразить
«домен одновременно в обоих списках»** — флаг на общей строке делает списки
взаимоисключающими. Пользователь явно сформулировал требование: это **два
независимых списка**, домен может быть в обоих.

### Решение

- **Отдельная таблица `wishlist`**, полностью независимая от `user_domains`:
  `id` PK, `user_id` FK→`users.id` `ON DELETE CASCADE`, `domain` (punycode),
  `registrable_domain` (для WHOIS-джойна, как у `user_domains`, ADR 035),
  `is_subdomain`, `added_at`, `last_notified_at` (nullable, audit одноразового
  уведомления). `UNIQUE(user_id, domain)` (`uq_wishlist_user_domain`); индексы
  по `user_id`, `domain`, `registrable_domain`. **Флаги `notify_*` в wishlist не
  нужны** — это разовая «слежка за освобождением», а не мониторинг.
- **Флаг `is_wishlist` на `user_domains` упраздняется.** Миграция переносит
  существующие `is_wishlist=True`-строки в таблицу `wishlist` (без потери
  `added_at`/`registrable_domain`/`is_subdomain`), удаляет их из `user_domains`,
  затем `DROP COLUMN is_wishlist`. Конфликтов данных нет: сейчас ни один домен
  не может быть одновременно tracked и wishlist (взаимоисключение), поэтому
  перенос 1:1. Downgrade — обратимый (вернуть колонку, перелить данные назад).
- **Независимые операции в карточке `/whois`.** follow/unfollow работает с
  `user_domains` как раньше; добавление/удаление wishlist — с таблицей
  `wishlist`. Карточка показывает **две независимые пары**: follow ↔ unfollow и
  «🎯 в wishlist» ↔ «убрать из wishlist» (по фактическому членству).
- **WHOIS-проверка wishlist-доменов** по-прежнему опирается на `whois_cache`
  (`next_check_at`), который не зависит от `user_domains`. Триггер освобождения
  (`check_domain._enqueue_wishlist_notices`) и `notify_wishlist` читают
  подписчиков из таблицы `wishlist`, а не из `user_domains.is_wishlist`.
  Домен, у которого есть и tracking-, и wishlist-подписчики, планируется как
  обычный отслеживаемый (registered-TTL); wishlist-only сохраняет своё
  поведение.
- **Лимит wishlist считается по таблице `wishlist`** (независимо от
  `user_domains`), порог — тот же `limits.max_domains_per_user` (отдельную квоту
  можно ввести позже).

### Технические инварианты (защитить тестами)

- Добавление домена в wishlist **не трогает** строку `user_domains`: tracked
  домен остаётся в `/list` и одновременно появляется в `/wishlist`.
- Снятие со слежения и удаление из wishlist — независимы: одно не удаляет другое.
- Карточка `/whois`: если домен в wishlist — показывается кнопка «убрать из
  wishlist»; если нет — «добавить в wishlist». Аналогично follow/unfollow.
- Одноразовость уведомления об освобождении сохранена (после отправки запись
  удаляется из `wishlist`).
- Миграция применяется на **Postgres** и обратима (round-trip, smoke-тест
  TASK-0009). Перенос is_wishlist→wishlist без потери и без дублей.
- Anti-drift: после упразднения `is_wishlist` — `grep` всех обращений к полю;
  моки со `spec`/`autospec` (CLAUDE.md). Ни одной ссылки на `is_wishlist` не
  остаётся.

### Альтернативы

- **Второй булев флаг `is_tracked` на `user_domains`** (строка живёт, пока домен
  хотя бы в одном списке). Меньшая миграция, но перегружает строку двумя
  независимыми членствами при одном наборе `notify_*` — семантически мутно;
  отвергнуто в пользу чистого разделения (выбор владельца).
- **Оставить флаг, но запретить конвертацию** — не решает требование «домен в
  обоих списках».

### Следствия

- Патч-релиз **v0.11.1**, есть миграция (новая таблица + перенос + drop колонки).
- Новых внешних зависимостей нет.
- Исполнение — TASK-0031 (схема + миграция) → TASK-0032 (развязка точек
  `is_wishlist` + кнопка «убрать из wishlist» + локали). Цепочка
  последовательная (0032 depends_on 0031).
- Закрывает оба UX-дефекта wishlist, доводит ADR 034 до полной независимости
  списков.

## 040. Углублённый почтовый слой + on-demand deep-views в карточке /whois (v0.13)

**Статус:** принято (решение владельца 2026-05-31). Развивает ADR 036
(email-intel) и ADR 037/038 (поддомены).

### Контекст

Базовый почтовый слой (ADR 036, v0.10) собирает MX/SPF/DMARC/DKIM и шлёт
алерты на изменения, но: (1) это лишь базовая диагностика (режим SPF по
`*all`, без рекурсии `include`; DKIM по словарю селекторов); (2) **на практике
блок почты не виден в карточке** — `format_email_block` возвращает пусто, пока
кэш не наполнен, а первый `/whois` отвечает синхронно, ставя `check_email_intel`
в очередь, и карточка не авто-обновляется; (3) перечень поддоменов живёт в
отдельной команде `/subdomains`, не привязан к карточке домена. Владелец
запросил: углубить почтовый аудит, вынести MX наверх (в первое сообщение рядом
с A/DNS/SSL), а полный почтовый разбор и поддомены — за отдельные кнопки.

### Решение

**1. Расклад карточки `/whois`.**
- **Инлайн (первое сообщение):** к существующим блокам WHOIS/DNS/SSL добавляется
  компактная почтовая строка — **MX-хосты + краткий статус** (режим SPF и
  политика DMARC, 1–2 строки). Это «здоровье почты с одного взгляда».
- **За кнопками (on-demand):** «🛰 Поддомены» и «✉️ Глубокий e-mail» — каждая
  по нажатию ставит ARQ-задачу, отвечает «⏳ ищу…», затем досылает/редактирует
  сообщение с результатом (паттерн `/subdomains`, ADR 037). Кнопка поддоменов
  **переиспользует** существующий enumeration-поток (ADR 037), не дублируя его.

**2. Углублённый почтовый разбор (deep email).** Расширенный сбор по запросу
(не в периодическом мониторинге v0.10 — держим нагрузку и объём ограниченными):
- **SPF include-резолвинг.** Рекурсивный разбор `include:`/`redirect=` со
  счётчиком DNS-lookups и лимитом **10** (RFC 7208 §4.6.4); флаг превышения
  лимита; перечисление итоговых источников. Чистая функция-резолвер с инъекцией
  DNS-резолвера (для тестов).
- **MTA-STS.** TXT `_mta-sts.<domain>` (наличие/версия) + загрузка policy-файла
  `https://mta-sts.<domain>/.well-known/mta-sts.txt` (mode: enforce/testing/none,
  список `mx`, `max_age`). HTTP — через `aiohttp`, timeout, **без follow
  redirects, лимит размера тела**, graceful degradation.
- **TLS-RPT.** TXT `_smtp._tls.<domain>` — наличие, `rua`.
- **DANE/TLSA.** TLSA на `_25._tcp.<mx-host>` для каждого MX-хоста (top-N);
  наличие записей. Полезно вместе с DNSSEC-статусом из WHOIS.
- **BIMI.** TXT `default._bimi.<domain>` — наличие, ссылка на логотип (`l=`) и
  VMC-сертификат (`a=`).
Результат — отдельное сообщение «карта почтовой зрелости», без алертов
(периодический мониторинг этих записей — потенциальный будущий ADR).

**3. Фикс «свежести» инлайн-блоков.** При первом `/whois`, когда кэш
SSL/DNS/email пуст, вместо пустоты показываем плейсхолдер «⏳ собираю
SSL/DNS/MX…» и явный хинт нажать «🔄 Обновить» через несколько секунд.
(Альтернатива — авто-edit сообщения воркером — вынесена как возможный
будущий шаг, требует прокидывания chat_id/message_id в задачу.)

### Технические инварианты (защитить тестами)

- SPF include-резолвер — чистая функция с инъекцией резолвера; юнит-тесты:
  вложенные `include`, `redirect`, циклы (защита от бесконечной рекурсии),
  превышение лимита 10 lookups, отсутствие записи.
- MTA-STS policy-fetch: timeout, **no-redirect**, лимит размера, недоступность
  ≠ падение (graceful degradation → «недоступно»). Парсер policy — чистая
  функция (enforce/testing/none, mx[], max_age), юнит-тесты на edge-кейсы.
- Все deep-парсеры (TLS-RPT/TLSA/BIMI) — чистые функции, отсутствие записи —
  валидное состояние, не ошибка.
- On-demand задачи защищены redis-флагом in-progress (как `check_subdomains`);
  callback'и в пределах 64 байт Telegram (idx, не полный FQDN — урок TASK-0024).
- Deep-сбор бьёт DNS/HTTP **только по запросу**; никакого фонового трафика.
- Инлайн-почта: пустой кэш → плейсхолдер, не «ничего»; MX/SPF/DMARC
  экранируются `html.escape` (как TASK-0037).
- Все строки — локали ru/en (инвариант `test_all_ru_keys_present_in_en`).

### Альтернативы

- **Углубить периодический мониторинг (алерты на MTA-STS/DANE/BIMI)** — отвергнуто
  в этом релизе: больше DNS/HTTP-трафика и схемных полей; начинаем с on-demand
  показа, мониторинг — позже отдельным ADR при спросе.
- **Полноценный SPF-аудит с оценкой механизмов и проверкой IP** — избыточно;
  ограничиваемся резолвингом include + счётчиком lookups (главный практический
  дефект — превышение 10 lookups).
- **Авто-обновление карточки воркером** — лучший UX, но требует прокидывать
  chat/message в ARQ и редактировать сообщение из задачи; вынесено в будущее,
  сейчас — плейсхолдер + refresh.
- **Отдельная команда вместо кнопок** — у нас уже есть `/subdomains`; владелец
  просил привязку к карточке, поэтому кнопки на карточке (переиспользуя поток).

### Следствия

- Минорный релиз **v0.13.0**. Возможна миграция (если кэшируем deep-результаты
  отдельными полями/таблицей с коротким TTL); базовый вариант — без новой
  периодики.
- Новых внешних зависимостей нет (DNS — `dnspython`, HTTP — `aiohttp`, оба есть).
- Исполнение — TASK-0038 (deep-парсеры/коллекторы) → 0039 (on-demand ARQ + кэш) →
  0040 (инлайн MX+статус + фикс свежести) → 0041 (кнопка «Глубокий e-mail») →
  0042 (кнопка «Поддомены») → 0043 (аудит v0.13) → 0044 (релиз v0.13.0).
- После каждого крупного раздела — комплексный аудит (конвенция CLAUDE.md).

## 041. FSM-состояния в Redis (MemoryStorage → RedisStorage, v0.14)

**Статус:** принято (стабилизационный релиз v0.14). Followup к ADR 033.

### Контекст

Dispatcher собирается с `MemoryStorage()` (`src/bot/app.py`). Все FSM-флоу
(`AwaitingDomainArg`, `ListSearchStates`, `NotifyDaysStates`,
`NotifySslDaysStates`, `NotifySubdomainIntervalStates`, `DownloadStates`,
`SettingsStates`) живут в памяти процесса. Следствия:
- **State теряется при рестарте бота.** Бот — webhook, рестартует на каждом
  деплое; пользователь в середине флоу (вводит дни/интервал/домен) теряет
  контекст без объяснения.
- **Нет настоящего time-based TTL.** Заброшенный флоу висит, пока его не
  собьёт middleware `clear_state_on_command` (срабатывает только на новую
  команду). «Тихо заброшенный» state не истекает.

Redis уже есть в инфраструктуре (ARQ-очередь, кэш-гарды) — переиспользуем.

### Решение

- **`RedisStorage` aiogram** на том же Redis-инстансе, что ARQ (URL из конфига).
- **`state_ttl` и `data_ttl`** (напр. 300 c = 5 мин) — заброшенный флоу истекает
  сам, без middleware-костыля.
- **Namespacing ключей.** Свой `key_builder`/префикс (напр. `fsm:`), чтобы
  FSM-ключи не пересекались с ARQ/кэш-ключами в общем Redis.
- **`clear_state_on_command` остаётся** — он решает другую задачу (сбросить
  незавершённый флоу при явной новой команде), это не дублирует TTL.
- **Грейсфул-старт.** Redis обязателен для бота и так (webhook + ARQ); если
  отдельная конфигурируемость нужна — `REDIS_FSM_TTL` в settings (дефолт 300).

### Технические инварианты (защитить тестами)

- State переживает «рестарт» (новый Dispatcher на том же Redis видит
  сохранённый state) — проверяется через `RedisStorage` на тестовом Redis
  (интеграционный, fakeredis/реальный).
- Заброшенный state истекает по `state_ttl` (проверка set→ожидание→get или
  мок времени/ttl).
- FSM-ключи неймспейснуты, не конфликтуют с ARQ.
- Существующие FSM-флоу не регрессируют (юнит-тесты хэндлеров со `spec`).

### Альтернативы

- **Оставить `MemoryStorage`** — статус-кво; теряем state на каждом деплое,
  нет TTL. Отвергнуто (плохой UX при росте частоты деплоев).
- **Своё хранилище** — избыточно, у aiogram есть `RedisStorage` из коробки.
- **Только nats/postgres-storage** — лишняя зависимость; Redis уже есть.

### Следствия

- Минорный релиз **v0.14.0** (стабилизация). Новых внешних зависимостей нет
  (Redis уже используется; `aiogram[redis]`/`redis` уже в стеке через ARQ —
  проверить экстру).
- Изменение точечное в `src/bot/app.py` + конфиг; нужен интеграционный тест
  на реальном/`fakeredis` Redis.

## 042. Админ/ops-слой: бекапы, отчёты, аудит-лог (v0.15)

**Статус:** принято (выбор владельца 2026-06-08). Развивает ADR 019 (админ-алерты,
`AlertService`, `admin_channel_id`) и существующий `daily_stats`.

### Контекст

Нужен операционный слой для эксплуатации прода: регулярные бекапы БД с
подтверждением, ежечасный пульс использования в админ-канал, ежедневная
графическая сводка и аудит-лог для разбора нештатных ситуаций. Часть основы
есть: `AlertService` (каналы #critical/#anomaly/#info/#daily, дедуп),
`send_daily_summary` (текст, 06:00 МСК), таблица `system_events` (аналитика,
retention 30д).

### Решения

**1. Бекапы Postgres (ежечасно, храним 36).** ARQ cron `backup_postgres`
(`minute={0}`): `pg_dump` через `asyncio.create_subprocess_exec` → gzip →
`BACKUP_DIR` (новый docker-том, переживает контейнер). Ротация — держим
`BACKUP_KEEP=36` свежих, старшие удаляем. **Положительная проверка:** файл
существует и непустой (> порога) **и** `pg_restore --list <dump>` завершается 0
(дамп структурно валиден). Результат (last_backup_at, size, ok, error)
пишется в Redis-ключ `ops:last_backup` (читает ежечасный отчёт). Redis **не**
бекапим (очередь/кэш/FSM регенерируемы). `pg_dump` требует
`postgresql-client-16` — добавляется в worker-образ (`Dockerfile`); версия
клиента = версии сервера (PG16).

**2. Ежечасный ops-отчёт.** ARQ cron `hourly_ops_report` (`minute={0}`):
краткая статистика за последний час (активные пользователи, lookups, новые
домены, ошибки/алерты) + статус бекапа из `ops:last_backup` → компактное
сообщение в админ-канал. Дедуп `AlertService` обойти (контент меняется
ежечасно): отдельный метод/severity `ops` без дедупа.

**3. Дневной графический отчёт (21:00 МСК).** ARQ cron `daily_graph_report`
(`hour={18}` UTC = 21:00 МСК): графики (matplotlib, backend **Agg**, headless)
— lookups/день, активные/день, новые домены/день, уведомления/день за ~14 дней
(GROUP BY day из timestamp'ов) → PNG в админ-канал. Текстовая сводка 06:00
(`send_daily_summary`) **остаётся**.

**4. Аудит-лог.** Таблица `audit_log` (PK, `created_at` index, `level`,
`category`, `actor` (user_id|"system"), `message`, `context` JSONB). Репозиторий
+ best-effort helper `audit(...)` (никогда не бросает — не ломает горячий путь).
Вписан в инцидент-точки: фейлы ARQ-задач, rate-limit hits, админ-действия,
webhook/startup-аномалии. **Отдельно** от `system_events` (та — аналитика
для сводок; `audit_log` — инциденты с контекстом). Retention **90 дней**
(cron-очистка, рядом с `cleanup_old_events`).

### Технические инварианты (защитить тестами)

- Бекап: ротация держит ровно `BACKUP_KEEP` файлов; verify ловит пустой/битый
  дамп (mock subprocess: rc≠0 → ok=False); статус пишется в Redis.
- Ежечасный отчёт не падает, если бекап отсутствует/упал — рапортует «бекап
  FAILED», а не крашится.
- `audit()` — best-effort: исключение внутри не пробрасывается в вызывающий код.
- Графики строятся headless (Agg, без DISPLAY); пустые данные не роняют рендер.
- Миграция `audit_log` применяется на Postgres и обратима (round-trip).
- Чувствительное не логируется/не шлётся (ADR 019): в ops-отчётах — только
  агрегаты; в audit context — без `BOT_TOKEN`/контактов/заметок.

### Альтернативы

- **Host crontab для бекапов** — вне git/ARQ-конвенции, и ежечасный отчёт не
  узнал бы статус; отвергнуто в пользу ARQ-задачи.
- **Reuse `system_events` под аудит** — разная семантика и retention (30 vs 90);
  отдельная `audit_log` чище.
- **Внешний chart-API (quickchart)** — сетевая зависимость против конвенции;
  matplotlib локально (Agg).
- **Бекап Redis** — не нужен (регенерируем); отвергнуто.

### Следствия

- Релиз **v0.15.0**; миграция (`audit_log`). Новые deps: **matplotlib** (Agg);
  worker-образ += `postgresql-client-16`; новый docker-том `backups`; новые env
  (`BACKUP_DIR`, `BACKUP_KEEP=36`, `audit_retention_days=90`).
- Исполнение — TASK-0057 (схема audit_log) → 0058 (бекапы) → 0059 (ежечасный
  отчёт) → 0060 (дневные графики) → 0061 (вписать audit() + retention) → 0062
  (аудит v0.15) → 0063 (релиз). Затем — **webapp (ADR 043, следующий этап)**.

## 043. Telegram WebApp (mini-app) — фронт + read/write API (v0.16)

**Статус:** принято (2026-06-08, по запросу владельца). Дизайн —
**`design/webapp/v1/`** (handoff дизайнера; источник правды по UI —
`design/webapp/v1/README.md`).

### Контекст

Бот — Telegram + фоновые проверки (WHOIS/SSL/DNS/email/поддомены). Нужен
визуальный слой для управления портфелем доменов из мобильного: дизайнер
прислал hi-fi Telegram-WebApp (6 экранов, дизайн-система PIN Voice, RU).
Сейчас в стеке нет ни фронта, ни HTTP-API: webhook-сервер — aiohttp
`web.Application` (`src/bot/webhook.py`, `/health` + aiogram-webhook), nginx —
reverse proxy (TLS 8443). Данные уже есть в БД (`user_domains` +
`whois/ssl/dns/email_intel/subdomain_enum`-кэши + `wishlist` + `audit_log`).

### Решение

**1. Тип.** Telegram **WebApp (mini-app)**, открывается из бота (кнопка/меню).
Вьюпорт даёт Telegram; нативка — `Telegram.WebApp` (`MainButton`, `BackButton`,
`HapticFeedback`, `themeParams`/`colorScheme`, `expand()`, safe-area).

**2. Backend — расширяем существующий aiohttp-app** (не новый фреймворк):
под-роутер `/api/webapp/*` (JSON) в `create_app`. Хэндлеры **тонкие** → сервисы/
репозитории (конвенция). Эндпойнты:
- read: `GET /portfolio` (серверная пагинация/поиск/фильтр/сортировка/группировка
  — на 50k), `GET /domain/{id}` (вкладки Обзор/WHOIS/SSL/DNS/Email/Поддомены),
  `GET /dashboard` (агрегаты/health/бюджет/риски), `GET /calendar?month=`,
  `GET /alerts`, `GET /settings`, `GET /groups`, `GET /wishlist`.
- write: тогглы уведомлений, добавить/снять домен, массовые действия, настройки,
  пометить алерты прочитанными, импорт CSV, wishlist — поверх существующих
  `DomainService`/репозиториев.
- **health-score** — перенести формулу из прототипа (`data.js`) на бэкенд
  (единый источник, не дублировать в JS).

**3. Auth — Telegram `initData`.** Каждый запрос несёт `initData`; бэкенд
**валидирует HMAC-SHA256** (ключ = `HMAC_SHA256(bot_token, "WebAppData")`) +
проверяет свежесть `auth_date` (TTL, напр. 24ч). Из `initData.user.id` → наш
`users`. **Stateless** (валидация на каждый запрос — дёшево); JWT-сессия —
опц. оптимизация позже. Bot-token **никогда** не уходит на фронт.

**4. Frontend — React + Vite (SPA).** Перенести токены PIN Voice
(`design/webapp/v1/app/ds/`) и нужные классы (`styles.css`/`tg.css`) **со
значениями as-is**; воссоздать 6 экранов (`screen-*.jsx`). Стек экранов поверх
5 вкладок таб-бара; «назад» → `Telegram.BackButton`; контекстные действия →
`MainButton`. Виртуализация списка (50k). Тема синхронизируется с Telegram.
**Не тащить из прототипа:** unpkg/Babel, «рамку телефона», сид-данные. Сборка —
статика, отдаётся nginx; `/api/webapp` — proxy_pass на bot-сервис.

**5. Безопасность.** initData-валидация + `auth_date` TTL; CORS только на origin
webapp; CSP; rate-limit API (переиспользовать `Limits`); пользователь видит
**только свои** домены (PII-скоупинг); React экранирует вывод; секреты не на
фронт.

**Replay protection (F10).** Отдельный nonce-store для предотвращения replay initData
не используется (принятый риск). Защита обеспечивается коротким TTL
`webapp_initdata_ttl` (дефолт 3600с после TASK-0083/F3). Захваченный initData
валиден ограниченное время. Документировано в контексте аудита v0.16.

### Технические инварианты (защитить тестами)

- initData с валидной подписью → 200; подделанная/просроченная (`auth_date`) →
  401 (unit на валидатор — известный тест-вектор Telegram).
- Replay-атаки ограничены коротким TTL `webapp_initdata_ttl` (нет отдельного nonce-store — принятый риск, см. F10).
- `/portfolio` отдаёт только домены текущего пользователя; пагинация/фильтры
  работают на стороне сервера.
- Запись (тоггл/add/remove) идёт через `DomainService` (не сырой SQL в хэндлере),
  ограничена лимитами, audit() на значимые действия.
- health-score на бэкенде совпадает с дизайн-формулой (тест на эталонных данных).
- Фронт: рендер экранов с мок-API; нет бандла unpkg/Babel; токены = значения из
  `ds/`.

### Альтернативы

- **Отдельный API-сервис** — оверкилл сейчас; расширяем webhook-app (общий
  lifecycle/БД), вынести позже при нагрузке (переклик с roadmap v1.0 «публичный
  API»).
- **Внешний веб (не mini-app)** — теряем нативную интеграцию/auth Telegram;
  отвергнуто.
- **Сессия через cookie/JWT с самого начала** — лишняя сложность; stateless
  initData-валидация проще и безопасна.
- **health-score в JS на фронте** — дублирование/расхождение; считаем на бэке.

### Следствия

- Релиз **v0.16.0** (webapp). Новый каталог фронта (`webapp/` — Vite-проект),
  новые backend-эндпойнты, nginx-конфиг (static + `/api/webapp` proxy), новые
  настройки (webapp origin, initData TTL). Миграций по данным, скорее всего, нет
  (используем существующие таблицы; «группы/теги» — проверить, есть ли модель,
  иначе мелкая миграция).
- Исполнение — TASK-0066 (backend auth+read API) → 0067 (frontend foundation:
  токены/chrome/Telegram SDK/роутинг/сборка+nginx) → 0068 (экраны: список +
  карточка домена) → 0069 (дашборд + календарь + алерты + «Ещё») → 0070 (write-
  действия API+фронт) → 0071 (аудит v0.16, security-heavy) → 0072 (релиз).
  Можно отгрузить read-only (0066–0069) как первую веху, действия (0070) —

## 044. DNS-отчёт — on-demand расширенный анализ всех записей (TASK-0090)

**Статус:** принято (2026-06-05, по запросу владельца).

### Контекст

В карточке `/whois` есть on-demand кнопки (поддомены — ADR 037, глубокий
e-mail — ADR 040). Запрос владельца: профессиональный инструмент анализа
домена — выгрузить ВСЕ DNS-записи, сгруппированные по типам, текстовым
файлом.

### Решение

Новая кнопка «🧾 DNS-отчёт» (`button.dns_report`) в `whois_actions`.
Callback `WhoisAction(action="dnsrep", domain=<исходный>)` — на ИСХОДНОЕ
имя (поддомен), а не registrable: DNS-записи принадлежат точному имени
(ADR 035). Action `dnsrep` (6 симв.) короче `refresh` (7) — не двигает
границу 64б callback.

Подсистема `src/dns_report/` (параллельна email_intel/dns_monitor):
- `client.fetch_dns_report` — async-обход через общий `build_resolver`
  (timeout/lifetime, override NS из настроек). Типы: SOA, NS, A, AAAA,
  CNAME, MX, TXT, SRV, CAA + DNSKEY/DS (признак DNSSEC). Обратные PTR для
  A/AAAA (лимит 16). Security-проба AXFR (трансфер зоны) у каждого NS —
  открытый трансфер = finding в отчёте.
- `formatter.format_dns_report` — текстовый файл, секции по типам в
  аналитическом порядке (зона→делегирование→адреса→почта→политики→
  безопасность), TTL у записей, перечень отсутствующих типов, сводка.
- `tasks/check_dns_report` — ARQ-задача, redis-guard, доставка
  `.txt`-файлом (`send_document`), при фейле — `deliver_ondemand_failure`
  (TASK-0086, не молчим).

### Инварианты

- **Без БД-кэша и миграций**: отчёт одноразовый, защита от спама — только
  redis-guard `dns_report_in_progress:<domain>` (TTL 90с).
- TXT — через `txt_to_str` (`rdata.strings`), НЕ `to_unicode` (урок 0089).
- Никогда не бросает: сбои отдельных типов → секция «Ошибки резолва»;
  полный провал (пусто + unreachable) → `DnsReportError` → сообщение юзеру.
- AXFR best-effort: исключения проглатываются, `axfr_open` ∈ {True/False/None}.

### Альтернативы

- **HTML/PDF-отчёт** — тяжелее, не нужен для текстовых DNS-данных; отвергнуто.
- **Кэш в БД** — отчёт ad-hoc и объёмный; redis-guard достаточно.
- **Запрос на registrable** — потеряли бы записи точного поддомена; на
  исходное имя корректнее (ADR 035).

## 045. «Свободен» только после верификации — RDAP-кросс-чек (TASK-0092)

**Статус:** принято (2026-06-07, по инциденту TASK-0091 / discozavr.ru).

### Контекст

Ручной тест: свободный домен зарегистрировали; внешние сервисы видят
регистрацию, бот 2+ суток показывал «свободен». Диагностика (TASK-0091):
relay/TCI отдавал легитимный «No entries found», парсер послушно верил
отсутствию записи. Для аудитории домейнеров ложное «свободен» — худший
ответ бота (провоцирует решения о покупке/ожидании).

### Решение

1. **Positive beats negative.** В `lookup_domain` (единственный entry-point
   WHOIS-ядра) добавлен шаг `_verify_unregistered`: если «свободен» пришёл
   из WHOIS-текста (`whois`, `proxy_whois`, `proxy_whois_ru`, `proxy_none`) —
   независимый RDAP-кросс-чек (IANA bootstrap, мимо relay/proxy):
   - RDAP found+registered → отдаём RDAP-данные (домен ЗАНЯТ),
     `raw_data.free_contradicted_whois_source` для отладки/алертов;
   - RDAP not_found → «свободен» подтверждён (`free_verified="rdap"`);
   - RDAP error/unsupported → `free_unverified=True`.
   «Свободен» от RDAP-источников (`rdap`, `proxy_rdap`) не перепроверяется —
   это уже авторитетный 404.
2. **Сбой ≠ свободен.** `looks_like_upstream_error`: текст
   рейтлимита/заглушки/HTML (`UPSTREAM_ERROR_PATTERNS`) → `WhoisError
   (unavailable)`, а не парсинг. Guard стоит в `proxy_client`
   (whois/whois_ru_upstream) и в direct WHOIS:43 пути.
3. **Честный UX.** Неподтверждённый «свободен» рендерится осторожно:
   «записи в WHOIS не найдено… подтвердить по второму источнику (RDAP)
   не удалось» (`commands.whois.free_unverified`), вместо уверенного
   «свободен для регистрации».

### Инварианты

- Зарегистрированные домены и WhoisError верификация не трогает
  (ноль лишних RDAP-запросов в горячем пути).
- Стоимость: +1 RDAP-запрос ТОЛЬКО на ответы «свободен» из WHOIS-текста.
- `free_verified`/`free_unverified` живут в `raw_data` (JSONB кэша) —
  без миграции схемы.

### Альтернативы

- **DNS-кросс-чек (NS-записи)** — не ловит незделегированные новореги
  (сам discozavr.ru на момент инцидента не имел NS); отвергнут как
  основной, возможен как дополнительный сигнал позже.
- **Тристейт `is_registered`** — честнее, но затрагивает всю схему/UI;
  флаги в raw_data решают задачу без миграции.
- **Чинить только relay** — нужно (инфра-таск), но бот не должен слепо
  доверять одному источнику в принципе.

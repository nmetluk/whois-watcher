# Воркфлоу проекта whois-watcher

> Заменяет прежний процесс «ручной промпт + Telegram-пинг + монолитный
> `SESSION_LOG.md`». Краткий контракт — в `handoff/README.md`; здесь —
> подробности для исполнителя и архитектора.

## Роли и границы

| | Архитектор (Cowork) | Исполнитель (Claude Code) |
|---|---|---|
| Где | Claude Desktop, рабочая копия git | машина разработчика, git PAT |
| Делает | проектирует, формирует таски, ревью, merge | реализует таск, тесты, PR |
| Пишет в | `handoff/tasks/`, `docs/`, `CLAUDE.md` | код в `src/`, тесты, `docs/sessions/` |
| Push | таски/доки в `main` | feature-ветки `task/NNNN-slug` |
| Запрещено | — | писать в Google Drive / вне git |

Источник правды — **GitHub**. Cowork-папка архитектора не является
каналом передачи: всё, что должно дойти до исполнителя, должно быть
**запушено**.

## Цикл одной задачи

```
Архитектор                         GitHub (main)                Исполнитель
   │ new + заполнить тело              │                            │
   │ board → INDEX.md                  │                            │
   │ commit+push  ───────────────────▶ │  TASK-NNNN (open)          │
   │                                   │ ◀───────────── git pull ───│
   │                                   │            claim TASK-NNNN │
   │                                   │     ветка task/NNNN-slug   │
   │                                   │            (работа+тесты)  │
   │                                   │   docs/sessions/SESSION-…  │
   │                                   │ ◀─ push ветки + открыть PR │
   │ ревью PR (CI зелёный) ◀───────────│  TASK status: in_review    │
   │ merge ───────────────────────────▶│  TASK status: done (CI)    │
```

## Файл задачи

Лежит в `handoff/tasks/TASK-NNNN-slug.md`. Машиночитаемый frontmatter +
человекочитаемое тело по шаблону `handoff/templates/task.md`.

Frontmatter (минимальный набор):

```yaml
---
id: TASK-0001
title: Багфикс wishlist ↔ tracked
status: open            # open|claimed|in_review|blocked|done
milestone: v0.8.1
adr: 034
area: code              # code|docs|infra|audit
depends_on: []          # [TASK-0000]
branch: ""              # task/0001-... (заполняет claim)
owner: ""               # исполнитель
session: ""             # docs/sessions/SESSION-...md (заполняет исполнитель)
pr: ""                  # ссылка/номер PR
created: 2026-05-28
---
```

Тело задачи обязано быть **самодостаточным**: исполнитель в новой сессии
не видел чат архитектора. Включать: цель, контекст/корень проблемы,
точные изменения по файлам, инварианты, требования к тестам, критерии
приёмки (Definition of Done), миграции, ссылки на ADR/файлы.

## Правила веток и коммитов

- Ветка: `task/NNNN-slug` от свежего `main`.
- Коммиты атомарные, в стиле репо (`feat:`, `fix:`, `docs:`, `chore:`).
- Сообщение ссылается на таск: `fix(wishlist): promote on /add (TASK-0001)`.
- Прямой push в `main` — только архитектор (таски/доки). Код — через PR.

## Обязательные проверки исполнителя (Definition of Done)

Перед переводом в `in_review`:

1. `python scripts/handoff.py validate` — frontmatter/статусы валидны.
2. Тесты: `uv run pytest` (или релевантная часть, но перед PR — полный).
3. Линт/типы: `uv run ruff check src tests`, `uv run black --check src tests`,
   `uv run mypy src`.
4. Миграции (если схема менялась): `alembic upgrade head` применяется
   на чистой БД без ошибок.
5. Per-session отчёт создан в `docs/sessions/` и прописан в `session:`
   таска.
6. `handoff.py status TASK-NNNN in_review`, push ветки, открыть PR
   (шаблон `.github/pull_request_template.md`).

CI (`.github/workflows/ci.yml`) повторяет 2–3 на стороне GitHub и
является блокирующим гейтом на merge.

## Per-session отчёты (взамен SESSION_LOG.md)

Каждая сессия исполнителя оставляет **один** файл
`docs/sessions/SESSION-NNNN-slug.md` по шаблону
`handoff/templates/session-report.md`. Это и есть носитель контекста для
следующей сессии: что сделано, что осталось, какие открытые вопросы,
какие решения приняты.

Старый `SESSION_LOG.md` заморожен (исторический), новые записи туда не
добавляются.

**Публичный репозиторий** — в отчёты НЕ писать: реальные домены/ID
пользователей бота, runtime-метрики прода, значения из `.env`, секреты.
Можно: имена файлов, коммиты/теги, ADR, имена тестов, агрегаты
(«493 tests passing»), открытые архитектурные вопросы.

## Перенос контекста между сессиями

Любая новая сессия начинает с чтения, в порядке:

1. `handoff/README.md` — протокол.
2. `handoff/STATE.md` — где мы сейчас, что следующее, активные решения.
3. `handoff/INDEX.md` — доска задач со статусами.
4. Свой `handoff/tasks/TASK-NNNN-*.md` — тело задачи.
5. Последние `docs/sessions/SESSION-*.md` по связанным таскам.

`STATE.md` обновляет архитектор после merge крупных кусков; исполнитель
обновляет раздел «Последняя сессия».

## Комплексный аудит после крупного раздела

После завершения **крупного раздела** (майлстоун / группа связанных
тасков) архитектор заводит аудит-таск (`area: audit`) и аудит
выполняется в **отдельной сессии**. Направления как минимум:

- **Безопасность** — секреты, ввод, инъекции, права, supply-chain
  (зависимости), логирование чувствительного.
- **Архитектура** — соответствие ADR, границы подсистем, связность,
  тех-долг.
- **Производительность** — горячий путь, async-инварианты, индексы БД,
  N+1.
- **Тесты** — покрытие критичной логики, флаки, реальные сценарии.
- **Кроссплатформенность** — пути, окончания строк, shell-зависимости.
- **Документация** — актуальность CLAUDE.md/ADR/STATE.

Результат — отчёт `handoff/audits/AUDIT-YYYY-MM-DD-area.md` по шаблону,
findings конвертируются в новые таски. Запустить скелет:
`python scripts/handoff.py audit --section "v0.9.0 поддомены"`.

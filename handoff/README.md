# Handoff — протокол обмена «архитектор ↔ исполнитель»

> **Start here.** Этот файл — единственная точка входа в рабочий процесс
> проекта. Его должен прочитать любой агент (или человек), впервые
> попавший в репозиторий, прежде чем что-либо делать. Он самодостаточен:
> по нему можно восстановить контекст «с нуля» в новой сессии.

## Зачем

Проект ведётся в распределённой схеме, где **каждый шаг выполняется в
отдельной сессии** (часто на разных машинах и ОС). Контекст между
сессиями не сохраняется в голове агента — он сохраняется **в файлах в
git**. GitHub — единственный источник правды.

Две роли:

- **Архитектор** — работает в Cowork (Claude Desktop). Проектирует,
  декомпозирует, **формирует файлы задач** в `handoff/tasks/`,
  коммитит и **пушит их сам**, ревьюит результаты и **мержит PR**.
- **Исполнитель** — Claude Code на машине разработчика (имеет git PAT).
  **Подхватывает** задачу из `handoff/tasks/`, выполняет в отдельной
  ветке, пишет per-session отчёт, открывает PR, пушит.

## Жёсткие правила (инварианты процесса)

1. **GitHub — источник правды.** Любой статус, решение, артефакт
   существует, только если он закоммичен и запушен. Слова в чате —
   нет.
2. **Исполнителю запрещено писать в Google Drive / любые внешние
   хранилища.** Только git push в GitHub. Cowork-папка архитектора
   (`Documents/Claude/Projects/...`) — рабочая копия архитектора, не
   канал обмена.
3. **Один таск — одна ветка — один PR.** Ветка: `task/NNNN-slug`.
   Прямой push в `main` запрещён (кроме архитектора, пушащего файлы
   задач/документацию).
4. **Кроссплатформенность.** Никаких предположений об ОС. Все
   служебные операции — через `scripts/handoff.py` (чистый Python,
   stdlib, работает на Windows/macOS/Linux). Не закладывать bash-only
   шаги в обязательный путь.
5. **Минимум ручных команд.** Если действие повторяется — оно должно
   быть в `handoff.py` или в CI, а не в голове исполнителя.
6. **Каждый завершённый таск оставляет per-session отчёт** в
   `docs/sessions/` (см. шаблон). Без отчёта таск не считается готовым.
7. **После каждого крупного раздела — комплексный аудит** в отдельной
   сессии (безопасность, архитектура, производительность, тесты,
   зависимости, кроссплатформенность). См. `handoff/audits/`.

```

├── audits/              # отчёты аудита AUDIT-YYYY-MM-DD-area.md
└── templates/           # шаблоны task / session-report / audit

docs/
├── workflow.md          # подробный воркфлоу (для людей и агентов)
└── sessions/            # per-session отчёты SESSION-NNNN-*.md

scripts/
└── handoff.py           # кроссплатформенный CLI управления задачами
```

## Жизненный цикл задачи (гибрид: статус-файл + PR)

Статус живёт во frontmatter файла задачи (для переноса контекста между
сессиями) **и** дублируется веткой/PR (для ревью и мержа).

```
open ──claim──▶ claimed ──(работа, PR открыт)──▶ in_review ──(merge)──▶ done
                   │                                  │
                   └────────────── blocked ◀──────────┘
```

| Статус | Что значит | Кто ставит |
|--------|-----------|-----------|
| `open` | задача сформирована, ждёт исполнителя | архитектор |
| `claimed` | взята в работу, заведена ветка `task/NNNN-slug` | исполнитель |
| `in_review` | PR открыт, прогон CI зелёный, ждёт ревью | исполнитель |
| `blocked` | заблокирована (см. поле `blocked_reason`) | любой |
| `done` | PR смержен в `main` | архитектор |

## Быстрый старт

**Архитектор — поставить задачу:**
```
python scripts/handoff.py new --title "Краткое название" --milestone v0.8.1 --area code
# заполнить тело файла handoff/tasks/TASK-NNNN-*.md по шаблону
python scripts/handoff.py board        # пересобрать INDEX.md
git add handoff/ && git commit -m "task(NNNN): краткое название" && git push
```

**Исполнитель — взять и сдать задачу:**
```
git checkout main && git pull --rebase origin main   # ОБЯЗАТЕЛЬНО: свежий main
python scripts/handoff.py list --status open
python scripts/handoff.py claim TASK-NNNN     # ставит claimed + создаёт ветку
# ... работа, тесты, per-session отчёт в docs/sessions/ ...
python scripts/handoff.py status TASK-NNNN in_review
git push -u origin task/NNNN-slug             # затем открыть PR
```

**Архитектор — принять:**
ревью PR → merge в `main`. После merge:
`python scripts/handoff.py done TASK-NNNN` (или авто-проставление в CI).

## Правила, нарушение которых ломает мерж (read this)

Эти пункты выведены из реальных инцидентов на TASK-0002…0004. Нарушение
любого превращает приём задачи в ручную операцию с риском потерять чужой
код. Соблюдать строго:

1. **Ветку резать ТОЛЬКО от свежего `main`.** Перед `claim` —
   `git checkout main && git pull --rebase origin main`. Иначе ветка
   тащит устаревшие файлы и при мерже **откатывает уже принятую работу**
   предыдущих тасков (PSL, миграции, бухгалтерию). Это случилось трижды.
2. **Статусы — только из набора** `open | claimed | in_review | blocked |
   done`. НЕ `completed`. Менять статус только через
   `scripts/handoff.py status`, не редактируя frontmatter руками
   (CLI заодно пересобирает `INDEX.md` и валидирует).
3. **`session:` — полный путь** `docs/sessions/SESSION-...md` (или
   принятый `YYYY-MM-DD_task-NNNN_*.md`) **с расширением `.md`**.
4. **Перед написанием миграции — узнать актуальный alembic-head.**
   `down_revision` обязан точно совпадать с id последней миграции на
   свежем `main` (см. `migrations/versions/`). Выдуманный id
   (`..._dns_cache` вместо `..._dns`) ломает `alembic upgrade head`.
   После добавления — проверить, что head единственный.
5. **Не трогать handoff-бухгалтерию чужих тасков** (STATE/INDEX/чужие
   `TASK-*.md`). Свой таск переводит исполнитель; `STATE.md` после merge
   крупных кусков ведёт архитектор.
6. **Один таск = одна ветка = один PR**, имя `task/NNNN-slug`.

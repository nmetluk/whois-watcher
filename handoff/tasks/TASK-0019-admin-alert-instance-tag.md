# TASK-0019 — Instance-тег в сообщениях админ-канала (ADR 019)

> 🟠 high (операционная боль: при нескольких деплоях не отличить, с какой
> машины алерт). Тело самодостаточно. Перед стартом:
> `git checkout main && git pull --rebase origin main`, затем `claim`.

## Цель

Каждое сообщение в админ-канал (ADR 019) начинается с идентификатора
инстанса: **label + домен + server IP** — чтобы при развёртывании на разных
машинах было видно, откуда сообщение. Пример: было `worker started` →
стало `[prod-admin · whois.example.com · 5.188.88.78]` + текст.

## Контекст / корень проблемы

При отладке нескольких деплоев на разных серверах сообщения вида `bot started`
/ `worker started` неразличимы — потеряли, какой сервер какой. Нужен
identity-префикс во ВСЕХ admin-сообщениях.

**Важно — конвенция:** `CLAUDE.md` (раздел «Логирование») сейчас запрещает
логировать runtime IP. Решение владельца: IP **разрешён в приватном
админ-канале** (ADR 019), но НЕ в structlog-логах. Эту правку конвенции надо
внести в этом же PR (см. ниже), чтобы код и доки не противоречили.

## Изменения по файлам

- `src/config/settings.py` — два новых поля (pydantic-settings, не magic):
  - `instance_name: str` (default `""`) — метка деплоя, напр. `prod-admin`.
  - `server_ip: str` (default `""`) — публичный IP, задаётся в `.env` каждого
    деплоя (НЕ автоопределение — без сетевых вызовов в рантайме).
  - Домен берём из уже существующего `webhook_base_url` (хост из URL).
- `src/services/alerts.py`:
  - Хелпер `instance_tag(settings) -> str` — собирает строку из непустых
    частей: `label · domain · ip` (пустые опускаем; если все пусты — тег
    пустой и ничего не ломается).
  - Вставить тег **централизованно** в единый chokepoint отправки —
    `AlertService._send` (перед `self._bot.send_message`) — чтобы тег получили
    ВСЕ типы сообщений: `send_critical` / `send_anomaly` / `send_info` /
    `send_daily_summary`. Проверить, что `send_daily_summary` тоже проходит
    через этот путь (если нет — покрыть и его).
  - Формат: первая строка `[<tag>]`, затем обычный текст (тег НЕ должен ломать
    дедупликацию — `_dedup_key` считать по исходным `severity/title/details`,
    БЕЗ тега, иначе одинаковые алерты с разных… нет, инстанс один — но всё
    равно дедуп по контенту без тега, чтобы поведение не менялось).
- `src/tasks/arq_config.py` — стартовое `send_info("worker started", …)` уже
  пойдёт через `_send` и получит тег автоматически; убедиться, что так же
  тегируется и стартовое сообщение со стороны бота (если есть в `main.py`/
  `app.py` — провести через `AlertService`, а не голый `bot.send_message`).
- `.env.example` — добавить `INSTANCE_NAME=` и `SERVER_IP=` с комментариями.
- `CLAUDE.md` (раздел «Логирование») — уточнить правило: runtime IP **не
  логировать в structlog**, но допускается в приватном админ-канале (ADR 019)
  через явный конфиг `SERVER_IP`. Чтобы доки ↔ код были согласованы.
- (Опц.) короткая приписка в ADR 019 (`docs/decisions.md`) про instance-тег.

## Инварианты (защитить тестами)

- Каждое отправленное admin-сообщение начинается с `[<tag>]`, когда хоть одна
  из частей задана.
- Если `instance_name`/`server_ip` пусты и домен недоступен — тег пуст,
  сообщение уходит без префикса и без ошибок.
- Дедупликация (`_dedup_key`) не зависит от тега (поведение не меняется).
- IP не утекает в structlog-логи (только в админ-канал).
